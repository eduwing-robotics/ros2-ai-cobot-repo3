# AUTOMATIC-SEQUENCE-STAGE-GATES — 지정한 단계까지만 자동 실행

분류: **SSOT**(`plan/`). 실기 자동 시퀀스를 한 번에 열지 않고, 주인님이 시작 전에 지정한
안전 체크포인트까지만 실행하는 순서와 승격 조건을 정한다. 안전 판정은
`contract/SAFETY-RULES.md`, 제안·승인은 `contract/VISION-CONTRACT.md`, 기존 수동 검증 순서는
`LAB-STEP-TEST-PLAN.md`가 정본이다.

## 결정

자동화의 단위는 개별 버튼이 아니라 **제한 실행(run with limit)** 이다.

1. 주인님이 `마지막 단계`와 현장확인을 고정하고 `자동 작업 시작`을 한 번 누른다.
2. 실행기는 현재 단계가 마지막 단계보다 앞일 때만 다음 단계에 들어간다.
3. 지정 단계가 완료되면 `HOLD`로 끝난다. 다음 동작을 제안·승인·전송하지 않는다.
4. 실행 중 마지막 단계를 늘릴 수 없다. 더 진행하려면 상태를 다시 확인하고 새 실행을 시작한다.
5. 새로고침·브리지 재접속·조종권 상실·DISARM 뒤에는 자동 재개하지 않는다.
6. 실기 명령 직전에 장부 기록·화면 갱신 같은 비동기 대기가 하나라도 있었다면 `runId`·상태·소유자·
   ARM·모드·속도·연결·터틀봇 정차를 다시 검사한다. STOP 후 깨어난 이전 코루틴은 다음 명령을 보내지 않는다.

`ARM`, 조종권 획득, 현장확인은 자동화하지 않는다. 이 셋과 `자동 작업 시작`은 사람의 경계이다.
단 첫 접촉 단계 S4는 실기 3/3 승격 전까지 낮은 파지 고스트를 세운 `PREVIEW`에서 명령 0건으로
멈추고, 사람의 `고스트 확인 · 집기 실행`을 한 번 더 요구한다. 그 외에는 지정 단계까지 중간
클릭이 없다. 기존 `한 칸씩` 실행은 진단·복구용으로 그대로 둔다.

## Impact Map Summary — S4 실측 총알 정합 (2026-09-10)

- 입력·정본: `POST /scan`의 최신 `carrier.bulletsUser1Mm`과 `carrier.user1Mm`; 새 좌표·새 API는 만들지 않는다.
- 소비자: `SimPanel → main → RobotTwin`의 고스트 표시와 `SimPanel → runContactCheck → composeDemoScene`의 MuJoCo 접촉 판정.
- 불변조건: 기대 총알 수가 아니면 하강 금지, 표시와 판정은 같은 배열, 배열 변경 시 엔진 장면 재생성, 현재 `PREVIEW`는 재사용 금지.
- 검증: 장면 XML에 검출 좌표가 들어가는 단위 검사, 총알과 툴의 접촉 회귀, 시뮬 탭 배선·브라우저 렌더, 배포 번들 대조.
- 배포: 화면·공유 모듈만 바꾸며 브리지는 재시작하지 않는다. 실기 모션 명령은 검증 범위 밖이다.

S4의 정렬·높이 조건은 표현이 아니라 승격 관문이다. 검출한 긴 변 요각만큼 TCP `rz`를 돌리고
IK가 J6를 포함한 전체 관절해를 다시 풀어, 손가락은 긴 변과 나란하고 개폐축은 변에 수직인 자세만
쓴다. 180° 동치 손목 해는 이 정렬을 바꾸지 않는다. 리프트 목표는 들린 거치대 바닥이 터틀봇의
라이다 포함 최고점보다 20mm 이상 높아야 하고, `close→lift` 관절 경로 접촉도 0이어야 한다. 장부에는
선택 J6·TCP `rz`·긴 변 요각과 라이다 위 여유를 함께 남긴다.

S4와 S7 내부의 미세 동작은 마지막 단계로 선택할 수 없다. 하강 직후나 물체를 닫은 채 낮은
자세는 안전한 정지점이 아니기 때문이다. 단, STOP은 단계와 무관하게 즉시 동작한다.
S3R은 예외가 아니라 **높은 안전 정지점**이다. 손끝은 파지 깊이보다 120mm 위에 있고 물체를
쥐지 않았으므로 여기서 HOLD할 수 있다. S3R은 S3의 미래 정차·놓기 전체 계획을 선행 조건으로
삼지 않고 완료 목록에도 S3를 넣지 않는다. S3를 골랐던 승인은 S3R 이동·그리퍼 명령까지 열지 않는다.

## 제한 실행 계약

시작 순간 아래 값을 한 번 복사해 실행 중 바꾸지 않는다.

```text
run = {
  runId, requestedLimit: S0..S8, status: RUNNING|HOLD|FAILED|STOPPED|COMPLETE,
  nextStage, completedStages[], startedAt,
  snapshot: {
    robotId, owner, phase, mode, speedOverridePct,
    handEyeCalibId, globalCalibId, carrierFrameAt,
    turtlebotId, turtlebotPose, turtlebotStopped
  }
}
```

- 시작할 때마다 **새 runId**를 만든다. 이전 `sessionStorage`의 runId·cursor·조준 자세를 잇지 않는다.
- 각 단계 진입 직전에 owner·ARMED·mode 0·속도·연결·안전 상태와 직전 단계 증거를 다시 읽는다.
- `nextStage > requestedLimit`이면 명령을 만들기 전에 `HOLD`로 끝낸다.
- S2 이후 물체 좌표가 바뀌거나 S5 뒤 터틀봇 자세가 바뀌면 기존 계획은 폐기하고 해당 관측
  단계부터 다시 푼다. 이전 계획으로 이어 가지 않는다.
- 실행 중 제한을 줄이면 현재 **원자 단계가 시작되기 전**이면 즉시 HOLD한다. 이미 원자 단계가
  시작됐으면 제한 변경을 받지 않고 STOP만 받는다.
- 새로고침·WebSocket 재접속·브리지 재시작 뒤 저장된 실행은 `ABANDONED`로 기록한다. 자동 재개는 없다.

## 실패와 정지

다음 중 하나면 커서를 전진시키지 않고 `FAILED`로 끝내며, 남은 제안은 승인하지 않는다.

- 같은 정지 자세 재촬영 3회 뒤에도 검출 없음·프레임 만료·캘리브레이션 ID 변경·뎁스 중심화 3패스 실패
- 총알 수 또는 위치 증거 부족, 두 긴 벽 모두 간섭 또는 IK 없음
- 선택한 상한에 필요한 계획의 IK·게이트·접촉 중 하나라도 결측 또는 빨강. S3R에는 현재
  자세→높은 접근 경로만 해당하며 미래 정차·놓기 구간은 해당하지 않는다
- owner·ARMED·mode·속도·터틀봇 정차 상태 변경
- 제안 거부·만료, 도착 readback 시간초과, 그리퍼 fault, 터틀봇 경로 없음·도착 실패

실패 뒤 자동 재시도는 **정차 상태의 읽기·스캔**에만 최대 횟수를 두고 허용한다. 모션 응답이
불확실하면 같은 명령을 자동 재전송하지 않는다. 화면 STOP은 FR5의 WebSocket과 `POST /stop`,
터틀봇 STOP을 함께 호출하고 결과를 보여야 한다.

활성화한다.

## 단계별 승격 규칙

다음 단계는 바로 구현하지 않는다. 현재 단계가 아래 세 관문을 모두 통과하고 주인님이 다음
마지막 단계를 명시해야 한 칸만 연다.

1. **목업·시뮬레이션**: 정상 경로와 검출 실패·proposal 만료·재접속·STOP 실패 주입에서
   지정 단계를 넘는 모션 호출이 0건이다.
2. **실기 단독 테스트**: 그 단계만 3회 연속 성공하고, readback·카메라 원본·runId가 남는다.
3. **회귀 게이트**: `sim-tab`, bridge, shared-unit, web 검증이 모두 통과한다.

| S5 | 왕복 주행 3회, 도착 허용오차 안, 주행 중 팔 모션 0건 |
| S6 | 터틀봇 정차 3곳에서 초록 거치대 중심·요각 허용오차 통과 |
| S7 | 놓기 3/3, 테두리 접촉·낙하 0, 반드시 후퇴 자세에서 끝남 |
| S8 | 3회 연속 다음 작업 대기 상태 일치, 장부 정상 종료 |

모든 단계가 통과해도 즉시 S8로 기본값을 바꾸지 않는다. 별도 전체 시퀀스 실기 한 번을
주인님이 승인한 뒤에만 `S8 전체`를 선택지로 승격한다.

## 구현 순서와 재사용점

1. `AimBlock.autoRun`을 재사용해 S1→S2를 잇되, 재중심 때 계산만 하고 끝내던 자리에 같은
   제한 실행 안의 `onGo`를 연결한다.
2. S3은 S2 완료 뒤 `SimPanel.solve()`로 전체 정차·놓기 계획을 만든다. S3R은 별도 준비 풀이로
   `approach`·`pregrip`만 풀며 `solve()`를 호출하지 않는다. 둘 다 새 조준값과 파지 벽 판정이
   같은 세대인지 확인한 뒤 시작한다.
3. S4 이후는 기존 `goNext()`의 한 칸 실행을 직렬 드라이버로 감싼다. 각 칸은 기존
   `/proposal → approve → 도착 확인`과 그리퍼 readback을 그대로 탄다.
4. 자동 실행 전 `VISION-CONTRACT.md`에 “한 번의 시작 승인이 지정 단계까지의 제한 실행을
   승인한다”를 먼저 추가한다. 새 모션 엔드포인트나 비전 전용 실행 경로는 만들지 않는다.

## 수렴 판정

- 채택: **불변 단계 상한 + 안전 체크포인트 + 단계별 승격**.
- 기각: 전체 자동 토글 하나, 하강·닫기 같은 미세 동작을 정지 단계로 노출, 새로고침 뒤 자동 재개,
  경로 없는 터틀봇 칸을 사람이 보냈다고 간주.
- 크럭스: 한 번의 시작 승인으로 여러 `proposal/approve`를 잇는 범위를 브리지 장부가 명확히
  증명할 수 있는가.
- 가장 싼 반증 실험: 마지막 단계를 **S3**으로 고정해 S0→S3을 한 번 실행하고, 중간에 재중심이
  발생하도록 글로벌 위치를 50mm 넘게 어긋나게 한다. 완료 장부에 S1·S2·S3은 있고 S4의
  proposal·gripper 명령이 **0건**이어야 한다. 이어서 브라우저 재로드를 주입해 자동 재개 0건을 확인한다.
