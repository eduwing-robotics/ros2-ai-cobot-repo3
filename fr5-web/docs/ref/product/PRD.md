# PRD — 무엇을 왜 만드는가

분류: **SSOT**. 범위가 헷갈릴 때 여기로 돌아온다.
갱신 2026-08-04 — **공정은 조립이다** (D66). 무대는 방산 탄두 라인이고(D51),
방향은 **부품을 합쳐 완성품을 내보내는 쪽**이다 — D50 이 정한 데모 과제(뚜껑 **체결**)와
같은 방향이다. 측정한다는 성격과
배치별 생산성 비교는 그대로고, **동작(궤적·정책)이라는 두 번째 축이 붙었다.**
그전 갱신(2026-07-30)은 과학실험실 무대로 주제를 확정한 것이었다.

## 목표 (확정)

> **방산 탄두 조립 라인에서 로봇팔과 AMR의 배치, 그리고 로봇이 움직이는 방식에 따라
> 생산성이 얼마나 달라지는가.**

이 프로젝트는 **측정**이다. 소프트웨어는 그 측정을 하는 **계기**다.

**축이 둘이다.**

| 축 | 무엇을 바꾸나 | 기능 |
|---|---|---|
| **공간** — 배치 | 팔·스테이션·AMR 경로를 어디에 두나 | F7·F8·F9 |
| **시간** — 동작 | 같은 작업을 **어떻게** 움직여 하나 — 사람 시연 그대로 / 후처리로 다듬은 궤적 / 학습된 정책 | **F10** (신설) |

둘째 축이 **와우모먼트**다. 같은 조립 작업의 시퀀스 타임이 화면에서 **사람 시연 → 후처리 →
정책** 순으로 줄어드는 것을 나란히 보여준다. 배치를 못 옮기는 자리에서도 생산성이 오른다.

**우리 몫은 시각화다.** 생산성 수치를 내는 알고리즘과 AMR 자율주행은 팀원이 맡는다
(`ARCHITECTURE.md` §우리 몫). 우리는 **맵을 편집하고, 받은 수치를 비교해 보여주고,
그 맵을 실물 위에 배치해 보이는 것**까지다.

그래서 우리가 지켜야 할 것은 둘이다 — **받는 모양을 우리가 먼저 제시하는 것**과
**나중에 데이터베이스·백엔드로 바꿔 끼울 수 있게 격리해 두는 것**.

## 문제

배치를 바꿔보려면 **실제로 장비를 옮겨야 한다.** 팔을 옮기고 작업대를 돌리고 AMR 경로를
다시 깔아야 하는데, 옮기기 전에는 그게 나은 배치인지 알 수 없다. 그래서 대개 안 바꾼다.

옮겨본 뒤에도 **무엇이 나아졌는지 숫자가 없다.** 시퀀스 타임을 손으로 재거나
"빨라진 것 같다"로 끝난다.

**그리고 배치를 못 옮기는 자리가 있다.** 조립 라인은 안전 격벽·컨베이어가 고정이라
팔을 옮길 여지가 별로 없다. 그 자리에서 남는 변수는 **로봇이 어떻게 움직이나**뿐인데,
사람이 손으로 가르친 궤적은 **손떨림과 느린 속도를 그대로 담고 있다.** 가르친 대로만
움직이면 사람보다 빠를 이유가 없다.

여기에 원래 문제가 겹친다 — 로봇 앞에 앉은 **한 사람만** 조작할 수 있고, 저장된 지점이
실제 공간의 어디인지는 관절 각도 숫자 6개로만 보여서 아무도 모른다.

## 만들 것

**맵을 화면에서 바꿔 생산성을 비교하고, 그 맵을 폰으로 실제 바닥에 배치해 검증하는 작업대.**

| # | 기능 | 완료 판정 |
|---|---|---|
| F1 | 웹에서 로봇 조작 | 팀원이 자기 노트북 브라우저에서 관절을 움직인다 |
| F2 | 화면 속 쌍둥이 | 실물이 움직이면 브라우저의 3D 로봇도 같이 움직인다 |
| F3 | 이동 지점 공유 | A가 저장한 지점을 B가 불러 재생한다 |
| F4 | 폰으로 실물 배치 | 앱 설치 없이 QR로 열어 실물 위에 지점·경로가 보인다 |
| F5 | 조종권 | 지금 누가 조종 중인지 보이고, 나머지는 관전한다 |
| F6 | 기록 | 명령·상태가 남고 나중에 되돌려 본다 |
| **F7** | **맵 편집** | 팔·스테이션·AMR 경로를 평면도에서 옮겨 저장한다. 도달 범위 밖이면 경고한다 |
| **F8** | **생산성 비교** | 맵 A와 B의 지표를 나란히 보고 **어느 쪽이 몇 % 나은지** 말할 수 있다 |
| **F9** | **맵 AR 검증** | 폰으로 실제 바닥에 맵을 배치해, 통로·작업대와 충돌하는지 눈으로 본다 |
| **F10** | **동작별 생산성 비교** | 같은 작업의 **사람 시연 · 후처리 궤적 · 학습된 정책**을 나란히 재생하고 시퀀스 타임을 % 로 말한다 |

F7~F9가 배치별 생산성 비교로 생긴 것이고, **F10은 2026-08-03 무대 고도화로 붙었다** (D51).
**F9는 F4의 확장**이고(같은 AR 화면에서 로봇 하나가 아니라 맵 전체), **F10은 F8의 확장**이다
— 같은 비교 화면에서 비교 대상이 맵 A·B 가 아니라 **같은 배치에서의 동작 A·B·C** 다.

F10은 새 파이프라인이 아니다. 세 값은 이미 사다리 위에 있다 — 시연 녹화(사다리 2) ·
후처리 궤적(사다리 2 후처리) · 정책(사다리 4). **재는 자리만 F8 화면에 하나 더 만든다.**

F1~F6은 그대로 필요하다. 배치를 바꾼 뒤 **실제로 한 시퀀스를 돌려야** 생산성이 나오고,
그걸 팀이 함께 보려면 F1~F5가 있어야 한다.

## 범위 밖 (이번에 안 한다)

- 역기구학 — **사람이 손끝 좌표를 쳐서 움직이는 것**은 안 한다. 저장된 관절 각도 재생으로
  충분하다. 단 **비전이 낸 제안에 한해 들어온다** (2026-08-13 · D131): 비전이 찾은 물체는
  **매번 다른 자리**라 저장 재생으로 못 덮는다. `contract/VISION-CONTRACT.md` §제안이 이미
  `targetPose.tcpMmDeg`(손끝 자리) → `moveJ` **번역**을 계약으로 세워 뒀고(D61) 그 번역이
  곧 역기구학이다 — **어긋나 있던 두 SSOT 를 PRD 쪽으로 맞춘다.** 열어도 **실행 경로는
  안 늘어난다**: 승인된 제안이 같은 게이트를 처음부터 다시 탄다.
  ⚠ **성공 판정은 안 바뀐다** — 이것은 F7~F10 **밖의 확장**이다
- mm 단위 정밀 정렬을 AR로 하는 것 — 마커 오차가 ±5~15mm라 불가능
- 자율 작업 계획 — **로봇이 스스로 목표를 세우는 것**은 안 한다. 사람이 가르친 것만 한다.
  단 "가르치는 방법" 에 **시연 학습(모방학습)이 들어온다** (2026-08-03 · D47):
  사람이 보여준 작업을 정책이 배워 재현하는 것까지가 범위이고, 배운 적 없는 새 작업을
  스스로 계획하는 것은 여전히 범위 밖이다
- **배치 최적화 자동 탐색** — 사람이 낸 맵 몇 개를 비교한다. 최적해를 찾지 않는다
- **실제 탄약·화약을 다루는 것** — 무대는 **시각 표현**이다. 실물 작업물은 페트병과 뚜껑이고
  (D50), 값·좌표·안전 판정은 전부 실물 기준이다. 이 결과물을 **검증된 탄두 조립 시스템으로
  제시하지 않는다** — 우리가 잰 것은 페트병으로 잰 것이다. 표시와 실물을 섞으면 화면이
  근거로 오해된다
- **생산성 수치를 내는 알고리즘** — 팀원 몫. 우리는 받아서 보여준다
- **AMR 주행 알고리즘** — 팀원 몫 (슬롯 스크립트로 꽂힌다). 단 **관제 인프라** —
  켜고 끄기·teleop·매핑·기록 대시보드 — 는 우리가 만든다 (`TB-CONTRACT.md` · D31)

## 미확정 — 무엇이 실제로 막히나

| 미확정 | 우리 진행이 막히나 | 누가 정하나 |
|---|---|---|
| 지표 데이터의 전달 방법 (HTTP·파일·DB) | **안 막힌다** — 목업으로 만들고 나중에 파일 하나 교체 | 팀 |
| 지표 필드 목록 | **안 막힌다** — 필수 둘만 있으면 화면이 돈다 | 팀 |
| ~~**한 시퀀스의 정의**~~ **풀렸다 (D51·D66) — 1발 조립 = 1시퀀스** | 안 막힌다 | — |
| 조립 공정 중 **어디까지를 로봇이 하나** (탄체 투입·신관 결합·검사·배출) | 부분 — 시퀀스 안의 공정 수 | 팀 |
| 실험 시나리오 (스테이션 종류·개수) | 부분 — F7의 편집 대상이 안 정해진다 | 팀 |
| ~~AMR 기종~~ **확정 — TurtleBot3 Burger ×2** (repo2 · D31) | 풀렸다 | — |
| 작업대 높이·실험실 실측 치수 | 부분 — 맵의 `z`, AR 정합 | 실측 |
| 맵을 어디에 저장하나 | **안 막힌다** — 같은 격리 경계를 쓴다 | 우리 |

**진짜 블로커였던 "한 시퀀스의 정의"가 무대 확정으로 풀렸다** — 1발 조립이 1시퀀스다.
남은 것은 목업과 격리 경계로 넘어간다 — 그게 팀원 일정에 우리가 묶이지 않는 방법이다.

## 성공 판정 (프로젝트 전체)

> **맵 두 개를 만들어, 맵 편집기에서 생산성 지표를 비교하고, 폰 AR로 두 배치를
> 실제 바닥에 배치해 확인한 뒤, "이 배치가 저 배치보다 몇 % 낫다"를 근거와 함께 말한다.**
>
> **그리고 같은 배치에서 같은 작업을, 사람이 가르친 대로 / 다듬은 궤적으로 / 학습한 정책으로
> 각각 돌려 "몇 % 빨라졌다"를 말한다.**

앞 문장이 되면 합격이고, **뒤 문장까지 되면 이 프로젝트의 와우모먼트**다.
기능이 아무리 많아도 앞 문장을 못 말하면 실패다.

**우리 쪽 판정은 여기서 한 겹 더 좁다** — 수치는 팀원이 낸다. 우리는
**그 수치가 들어오면 위 문장이 화면에서 나오는 상태**까지 만든다. 판정은 목업으로도 선다:
목업 두 개를 넣었을 때 비교 화면과 AR 겹치기가 정상 동작하고, 실물 수치로 바꾸는 작업이
**파일 한 개 교체**로 끝나면 우리 몫은 완료다.

원래의 판정(팀원 셋이 접속해 한 명이 조작하고 둘이 관전하며 폰으로 확인)은
**여기에 도달하기 위한 중간 판정**으로 남는다 — `MILESTONES.md` V1~V3.
