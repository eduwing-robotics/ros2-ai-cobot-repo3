# FR5 브링업 — 우분투 호스트에서 5분 안에 로봇 붙이기

분류: **SSOT**. 아침에 이것만 따라 한다. 왜 이런 구조인지는 D42·D45·D46,
막히면 §안 될 때 로 간다.

**주소 — 팀은 「호스트:5055」 하나만 안다. 그 호스트가 어느 쪽인지는 아래가 정한다.**
지금은 **윈도우 `http://192.168.30.18:5055`** (2026-08-27 확인 · D144). 우분투면 `192.168.30.240:5055`.
⚠ **이 숫자는 DHCP 라 또 바뀐다** — 안 맞으면 §윈도우 호스트 의 이름으로 다시 찾는다.

⚠ **호스트가 둘이다** (2026-08-11~). 로봇 랜선이 꽂힌 기계가 호스트이고, 랜선은 한 곳에만
꽂히므로 둘이 동시에 호스트일 수 없다. 아래 ①~④ 는 **우분투** 기준이고, 윈도우
(`192.168.30.18:5055`)면 §윈도우 호스트 로 간다. 어느 쪽이 살아 있나 — **`ping` 이 아니라**
`for h in 192.168.30.240 192.168.30.18; do nc -z -G 3 $h 22 && echo $h; done`

## 물리 확인 (1분)

1. 로봇 컨트롤러 전원 · 비상정지 버튼 **해제** 상태
2. 로봇 ↔ 우분투 **랜선** 연결 — **컨트롤러 1번 포트 · 우분투 내장 `enp3s0` 직결** (D105).
   우분투는 `192.168.58.10/24` + `192.168.57.10/24` **둘 다** 갖고, 로봇은 **`192.168.57.2`**.
   ⚠ **컨트롤러 포트가 곧 로봇 주소다** (D63) — **0번(비상정지 박스 쪽)이면 `58.2`,
   1번이면 `57.2`**. 주소가 다르면 컨트롤러를 의심하기 전에 **선이 몇 번에 꽂혔는지**부터 본다
   ⚠ **0번은 비상정지 박스를 경유해 100Mbps 가 강제된다** — 2026-08-10 에 그 경로로
   **0 바이트**가 됐다. 1번 직결은 같은 선·같은 날 **1Gbps · RTT 0.144ms** 였다 (D105)
   ⚠ **1번 포트에서는 펜던트 웹앱(`:80`)을 못 연다** — 그 UI 는 58 대역에만 붙는다 (D68).
   물리 티치펜던트로 본다. **D68 은 이 한 줄만 남고 배선 통일은 D105 가 뒤집었다**
   ⚠ **인터페이스 이름을 고정으로 읽지 않는다** — 이름은 세고 판정은 `carrier` 로 한다
   (§안 될 때). 지금은 내장 `enp3s0`, 우회로가 USB 어댑터(`enx7019887496bb`)다
3. 우분투 전원 · 팀 와이파이 접속

## 명령 (맥에서 전부 원격으로 · 4분)

```bash
# ① 로봇이 우분투에서 닿나 — 막히면 **선이 몇 번 포트인지**부터 본다 (1번=57.2 · 0번=58.2)
ssh ej@192.168.30.240 'ping -c 2 192.168.57.2'

# ② 브리지 살아 있나 (systemd 가 부팅 때 자동 기동한다 — 보통 이미 떠 있다)
rtk proxy curl -s http://192.168.30.240:5055/robots | head -c 60
#   비어 있으면: ssh ej@192.168.30.240 'export XDG_RUNTIME_DIR=/run/user/$(id -u); systemctl --user restart fr5-bridge'

# ③ 로봇 연결 (observe-only — 아직 명령은 못 보낸다)
#   ⚠ **랜을 방금 고쳤다면 ② 의 재시작을 먼저 무조건 한다** (2026-08-11 실측 · §안 될 때).
#     `ping` 이 0% 손실로 되살아난 직후에도 첫 connect 는 거부된다 — 브리지가 주소 없는 랜
#     위에서 떠 있었으면 SDK 플래그가 굳어 있다. 랜 복구 뒤 재시작은 선택이 아니다
rtk proxy curl -s -X POST http://192.168.30.240:5055/connect \
  -H 'Content-Type: application/json' -d '{"robotId":"fr5-lab-a","observeOnly":true}'
#   → {"ok":true,"phase":"OBSERVE_ONLY"}

# ④ 값이 흐르나
rtk proxy curl -s http://192.168.30.240:5055/state | python3 -m json.tool | head -20
```

**맥에서 `/state` 를 볼 때는 `rtk proxy curl` 을 쓴다** — 그냥 `curl` 로 파이프하면
rtk 훅이 출력을 510바이트에서 잘라 JSON 이 깨진 것처럼 보인다 (2026-08-03 실측·GAP CLOSED).

## 윈도우 호스트 — 상주 셋 (2026-08-19)

⚠ **주소는 DHCP 라 바뀐다** (2026-08-27 실측 — `.5` → `.18`). 그날 `.5` 는 **다른 기기가**
물고 있어서 핑은 되는데 22·5055 가 `Connection refused` 였다 — 「브리지가 죽었다」로 읽힌다.
**주소로 찾지 말고 이름으로 찾는다.** 호스트명 `DESKTOP-EAADSGE` 는 안 바뀌고 mDNS 가 뜬다:

```bash
dscacheutil -q host -a name DESKTOP-EAADSGE.local | grep ip_address
```

`.local` 이름은 **우리 CLI·SSH 에서만** 쓴다. 팀에 뿌리는 화면 주소는 **숫자로** 준다 —
안드로이드 크롬이 `.local` 을 해석하지 못해 **폰에서만** 조용히 안 열린다.
이름도 안 잡히면 대역을 훑는다 — `:22` 가 열린 곳이 그 기계다(윈도우는 ICMP 를 막는다).
**뿌리 해결은 공유기 DHCP 예약** — 사람이 해야 한다.

systemd 자리를 **작업 스케줄러**가 맡는다. 셋 다 **로그온 트리거**다.

| 작업 | 하는 일 | 로그 |
|---|---|---|
| `fr5-bridge` | 브리지 `:5055` + 받침 추적 | `%USERPROFILE%\fr5-bridge.log` |
| `fr5-cam-bridge` | 손목 카메라 관문 `:5058` | `%USERPROFILE%\cam-bridge.log` |
| `fr5-drift` | 글로벌캠 정합 감시 | `%USERPROFILE%\fr5-drift.log` |

실행기 **정본은 저장소**다 — `scripts/deploy/fr5-bridge.win.cmd` · `fr5-drift.win.cmd`.
호스트의 `%USERPROFILE%\*.cmd` 는 그 사본이다. 다시 깔 때:

```bash
scp scripts/deploy/fr5-bridge.win.cmd "heeyoung park@192.168.30.18:fr5-bridge.cmd"
scp scripts/deploy/fr5-drift.win.cmd  "heeyoung park@192.168.30.18:fr5-drift.cmd"
ssh -l "heeyoung park" 192.168.30.18 'setx FR5_CAM_HOST "192.168.30.8:8080"'
```

**폰 주소의 정본은 사용자 환경변수 `FR5_CAM_HOST` 하나다** (하드 룰 5). 브리지의 받침
추적(`main.py:652`)과 정합 감시(`watch-calib.py --host` 기본값)가 **같은 것을 읽는다.**
어느 한쪽 실행기에 주소를 다시 박으면, 폰이 바뀔 때 **한 곳만 고치고 나머지는 조용히 옛 폰을
본다** — 그 고장은 화면이 **초록인 채로** 난다.

⛔ **`uvicorn main:app` 로 부르지 마라** (2026-08-19 실측). `uv` 가 매번 새 venv 에 만드는
`uvicorn.exe` 는 서명·평판이 없어 **Smart App Control** 이 막는다(`os error 4551`) — 브리지가
아예 안 뜨고 화면이 통째로 안 나온다. `python -m uvicorn` 으로 부른다(python.exe 는 서명됐다).
**Smart App Control 을 끄지 마라 — 한 번 끄면 윈도우 재설치 전까지 못 켠다.**

⛔ **`Stop-ScheduledTask` 는 손자 프로세스를 안 죽인다** (2026-08-19 실측). `.cmd` 가 띄운
파이썬이 그대로 살아서, 재시작한 줄 알고 **옛 인자로 도는 프로세스를 새 것으로 착각한다.**
갈라내는 한 줄:

```powershell
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like "*watch-calib*" } |
  ForEach-Object { $_.ProcessId; $_.CommandLine }
```

⚠ **`fr5-bridge` 는 로봇이 붙어 있으면 재시작하지 않는다** — 조종권과 `ARMED` 가 풀린다
(하드 룰 3). 화면(`FR5/dist`)은 `StaticFiles` 가 요청마다 디스크를 보므로 재시작 없이 반영된다.

## 조작까지 (사람이 화면에서)

`http://192.168.30.240:5055` 를 열고 — 이름 입력 → **조종권 잡기** → `현장확인` 체크 →

## 안 될 때

| 증상 | 원인·조치 |
|---|---|
| ping 실패 | **유선 인터페이스를 세어 `carrier` 로 선이냐 주소냐부터 가른다** (이름을 박지 않는다 — 위 §물리 확인). `0` 이면 랜선, `1` 인데 `ip -brief addr` 에 **`192.168.57.10`** 이 없으면 유선 프로필이 안 올라온 것이다 → 아래 「링크는 섰는데 주소가 없다」 행. 링크만 보고 판단하지 않는다 — 1000Mb/s 로 잡혀도 주소가 없으면 못 간다. **보는 주소는 `57.10` 이다** — 로봇이 1번 포트라 `58.10` 만 있으면 링크가 멀쩡해도 못 간다 (2026-08-11 실측) |
| 꽂았는데도 `carrier: 0` | ⚠ **먼저 다시 꽂는다. 그 다음에 고장을 말한다** (2026-08-10 정정 — 이걸 안 해서 하루를 잃었다). 아침에 내장 `enp3s0` 을 「사망」으로 판정했는데(부팅별 `Link is Up` `9→1→0→0` · `modprobe` 무효 · 같은 케이블이 맥에서는 붙음) **오후에 다시 꽂자 `1Gbps/Full` 로 섰다. 접촉 불량이었다.** 근거 셋이 다 있어도 접촉을 먼저 배제해야 한다. 다시 꽂아도 `carrier: 0` 이면 그때 `sudo modprobe -r r8169; sudo modprobe r8169` → 그래도면 하드웨어다. 우회는 USB 랜 어댑터에 같은 주소를 물려주는 것이지만 **대가가 크다** (아래 행) |
| USB 랜 어댑터를 쓰고 있다 | ⚠ **가능하면 내장 포트로 되돌린다** (2026-08-10 실측 대조 · 같은 선·같은 컨트롤러 포트): 어댑터는 `100Mb/s`·`Duplex Unknown`·**RTT 평균 148ms(최대 1008ms)·지터 296**, 내장 직결은 `1000Mb/s/Full`·**RTT 평균 0.144ms**. **1000배다.** 그 어댑터는 `USB 10/100 LAN`(`1a86:e396` · wch.cn)이라 100Mbps 가 천장이고, `Duplex: Unknown` 은 **고장이 아니라 원래 안 보고하는 값**이다 — 판정선으로 쓰지 마라 |
| USB 랜 어댑터가 초 단위로 끊긴다 | **허브를 거치면 스스로 재열거한다** (2026-08-10 실측 · `1-1.3`→`1-1.4` 에서 같은 초에 disconnect+재등장 3회). 장치 번호가 늘어나는 것이 계수기다 — 본체 루트 포트(`1-9` 처럼 점 없는 이름)에 직결한다. 이 재열거가 `No route to host`·연결 끊김·타임아웃을 한꺼번에 만든다 |
| 링크는 섰는데 주소가 없다 | ⚠ **프로필을 이름으로 지목하지 않는다 — UUID 로 짚는다** (2026-08-11 실측 · 옛 서술 정정). 그날 호스트에 `Wired connection 1` 은 **아예 없었고 내장·USB 둘 다 `Wired connection 2`** 였다 — 이름으로 부르면 `no such connection profile` 이 나거나 엉뚱한 쪽을 고친다. 먼저 센다:<br>`nmcli -t -f UUID,TYPE connection show \| awk -F: '$2=="802-3-ethernet"{print $1}'` → 각 UUID 를 `nmcli -t -f connection.id,connection.interface-name,connection.autoconnect,ipv4.addresses connection show <UUID>` 로 본다.<br>실측 상태(2026-08-11): 내장 `enp3s0` 쪽은 **`autoconnect=no` · `58.10` 만**, `57.10` 은 **빠져 있는 USB 어댑터 프로필에만** 있었다 — 그래서 1Gbps 로 붙은 채 주소가 0개였다. 고치는 한 줄(sudo — 사람이 친다):<br>`sudo nmcli connection modify <내장UUID> +ipv4.addresses 192.168.57.10/24 connection.autoconnect yes && sudo nmcli connection up <내장UUID>`<br>⚠ **`never-default` 를 빼면 이 랜이 기본 경로를 뺏어 WiFi 로 들어온 사람이 쫓겨난다.** ⚠ **`ipv4.method` 는 반드시 `manual`** — `auto` 면 DHCP 를 기다리다 가진 주소까지 반납한다 (D63 ②) |
| sudo 를 못 쓴다 | **소프트웨어 우회는 없다** (2026-08-11 실측). SSH 세션은 polkit 이 로컬 활성 세션으로 안 봐서 `nmcli modify` = `Insufficient privileges`, `nmcli up` = `Not authorized to control networking` 이고 `ip addr add` 도 root 전용이다. 무비번 길은 **물리 하나** — 랜선을 `autoconnect=yes` 이고 주소를 가진 다른 랜카드로 옮긴다. USB 어댑터로 옮기면 붙긴 하지만 100Mbps·RTT 148ms 로 되돌아간다(위 행) — 계측용으로는 쓰지 않는다 |
| 설정 파일을 우분투에 넣을 때 | **답변의 코드블록을 복사해 붙이지 않는다.** 들여쓰기 공백이 NBSP(`cat -A` 에서 `M-BM-`)로 바뀌어 YAML 이 조용히 무효가 된다. `scp` 로 파일을 통째로 보낸다 (2026-08-04 실측) |
| `/robots` 무응답 | 서비스가 죽었다 → `systemctl --user restart fr5-bridge` · 로그 `journalctl --user -u fr5-bridge -n 50` |
| connect 가 **모델 불일치**로 거부 | 다른 개체가 배정됐다. `config.yaml` 의 `expectedModel` 과 실측을 대조 — **추측으로 고치지 않는다** |
| **게이트는 다 통과하는데 이동만 거부된다** (`code=172`) | ⛔ **전역 속도 오버라이드가 0% 다** — `172` = *"Motion Speed Cannot Be 0"* (정본: `fairino-doc-en.readthedocs.io/latest/SDKManual/errcode.html`). 펜던트에서 **속도를 0 이 아닌 값으로** 올린다. ⚠ **「펜던트로는 움직이니 속도는 아니다」로 배제하지 마라** — 펜던트 수동 조그는 **자기 속도**를 쓰고 오버라이드는 **프로그램·외부 명령에만** 걸린다. 2026-08-12 에 그 오판으로 호스트·포트·비상정지까지 헛되게 돌았다(반나절). ⚠ **전원 재투입 뒤에 확인한다** — 08-10 에 컨트롤 박스 전원을 두 번 껐다 켠 직후부터 이 증상이 시작됐고, 그 사이 아무도 관절을 안 움직여 08-12 까지 안 드러났다. 근거 `evidence/2026-08-12/movej-172-windows.md` · 같은 항목이 **2026-07-31 첫 이동 문서에도 이미 있었다** |
| **이동만 거부인데 172 가 아니다** | 화면에 뜬 코드를 그대로 본다 — `170` 사용자 좌표계 미적용 · `171` 관절 소프트리밋(보호 실패) 은 등재돼 있다(`fairino.ERROR_TRANSLATE`). 표에 없으면 위 정본 URL 에서 찾아 **등재하고** 나서 조치한다. **숫자만 보여주면 다음 사람이 같은 반나절을 쓴다** |
| **랜선을 0번↔1번으로 옮겼다** | ⚠ **공짜가 아니다.** 0번은 **비상정지 박스를 경유**해서, 꽂거나 뽑는 순간 `6-2`(슬레이브 상태 불일치 · **리셋 불가**)가 난다 — 2026-08-12 에 **두 번** 겪었고 둘 다 **컨트롤 박스 전원 재투입**으로만 풀렸다. 포트는 이동 거부의 원인이 **아니었다**(0번에서도 `172`). 옮길 이유가 없으면 옮기지 않는다 |
| connect 가 xmlrpc 실패 (`GetSoftwareVersion=-4`) | **순서를 지킨다 — 로봇 재부팅은 맨 마지막이다** (2026-08-05 실측). ⓪**비상정지 버튼부터 본다** — 제일 흔하고 제일 싸다. 지금은 브리지가 20004 를 읽어 `비상정지가 눌려 있다` 로 직접 말해 준다 (2026-08-08). 그 문구가 나오면 아래는 하지 않는다 ①**브리지를 재시작**한다 — 배포가 랜 링크 흔들림에 걸리면 `20003`·`20004` 에 **죽은 소켓**이 남아 링크가 돌아와도 계속 `-4` 를 낸다 (`ss -tnp \| grep 2000` 에 `SYN-SENT` 가 보인다). 오늘은 이 한 번으로 붙었다 ②`ping` 과 `ss` 로 로봇이 실제로 조용한지 본다 — **`20003` 이 TCP 는 받는데 응답만 없으면 세션이 남의 손에 있다** ③컨트롤러 재부팅. 20003 은 **연결 하나뿐**이라 브리지 밖에서 붙지 않는다 |
| 랜 속도가 바뀌었다 (`ethtool`) | **선이 옮겨졌거나 어댑터가 끼었다는 신호다.** 컨트롤러 1번 포트 + 내장 직결이면 **1Gbps**, 0번(비상정지 박스 경유)이면 **100Mbps 강제**, USB 어댑터를 끼면 어느 포트든 **100Mbps** (그 칩이 10/100 이다). 주소도 같이 바뀌었을 수 있다 (D63) |
| 링크는 정상인데 로봇이 조용하다 | **카운터를 먼저 읽는다 — `ip -s link show <IF>`** (2026-08-10 정정. 이걸 안 읽어 「랜선 불량」으로 두 번 오진했다). `RX errors`(CRC)가 0 이면 **선은 무죄**다. `carrier_changes` 가 안 늘면 **어댑터 재열거도 아니다**. 우리 `TX` 만 늘고 `RX bytes` 가 **한 바이트도 안 늘면** 상대가 침묵하는 것이다 → **컨트롤러 포트를 바꿔 본다**(0↔1). 0번에서 0 바이트, 1번에서 715KB 였다 |
| connect 가 **`프리플라이트 10s 무응답`** 으로 거부 | **랜을 방금 고친 직후면 원인은 로봇이 아니라 브리지다** (2026-08-11 실측). `ping` 0% 손실 · RTT 0.160ms · 1Gbps 인 상태에서도 첫 `connect` 가 이 사유로 거부됐다 — 브리지가 **주소 없는 랜 위에서 부팅 때 떠서** SDK 의 `RPC.is_conect` 가 굳었기 때문이다(아래 `-4` 행과 같은 뿌리인데 **증상이 `-4` 가 아니라 타임아웃으로 나온다**). `systemctl --user restart fr5-bridge` 한 번으로 **바로 `OBSERVE_ONLY`** 가 됐다. ⚠ **랜 복구 → 브리지 재시작은 순서가 아니라 짝이다** — 랜만 고치고 connect 를 두드리면 로봇·펜던트를 헛되게 뒤진다 |
| `-4` 가 계속 난다 | ⚠ **`-4` 를 "컨트롤러가 거부" 로 읽지 마라 (2026-08-10 정정 · 소스 확인).** SDK 의 `xmlrpc_timeout` 데코레이터는 클래스 변수 `RPC.is_conect` 가 `False` 면 **로봇에 묻지도 않고 `-4` 를 반환**한다. 그 값은 생성자의 1초짜리 `GetControllerIP()` 탐침이 실패할 때 내려가고 **다시 올리는 코드는 주석 처리돼 있다** — 즉 **랜이 1초만 끊겨도 브리지 프로세스가 영구히 `-4`** 를 낸다. **먼저 `systemctl --user restart fr5-bridge` 로 프로세스를 새로 띄우고 다시 시도한다.** 우리 어댑터는 `connect()` 마다 이 플래그를 되살리지만, 옛 배포본에는 그 수정이 없다 |
| 그래도 `-4` (컨트롤러 거부) | 펜던트에서 ①**제어권이 `Local` 이면 `Remote` 로 바꾼다** (외부 명령을 아예 안 받는다 · 강사 자료 Ch10 3-6-6 · 2026-08-05) ②서보 Enable ③자동 모드 ④전역 속도 0% 아닌지 — 이 순서로 본다 |
| 조그가 안 먹는다 | 1° 는 손끝에서 약 16mm 라 눈에 잘 안 보인다. `/state` 의 관절값 변화로 판정한다 |

## 비상정지를 눌렀다 — 복구 (2026-08-08 실기)

**순서가 전부다. 소프트웨어부터 만지면 30분 나간다.**

1. **버튼을 시계 방향으로 돌려 뽑는다.** 래치는 물리 구조라 재부팅으로 안 풀린다.
   **버튼은 하나가 아니다** — 컨트롤 박스와 펜던트 양쪽을 다 본다
2. `/state` 로 확인한다 — `emergencyStop: false` · `mainErrorCode: 0` 이 **둘 다** 돼야 한다
   ```bash
   ssh ej@192.168.30.240 'curl -s http://127.0.0.1:5055/state' | python3 -c \
     'import sys,json;print(json.load(sys.stdin)["safety"])'
   ```
3. 아직 `true` 면 **컨트롤 박스 전원 재투입** — 안전 릴레이가 래치된 경우다.
   끄기 전에 `POST /disconnect` 를 먼저 한다 (§끌 때)
4. **브리지 재시작** → `/connect` → 펜던트에서 서보 Enable

**`emergencyStop` 이 캐시인지 의심되면 브리지를 떼고 로봇에게 직접 묻는다.**
20004 는 xmlrpc 와 독립이라 급정지 중에도 흐른다 — 다만 **구독자를 하나만 받으므로**
`POST /disconnect` 로 브리지를 먼저 뗀다. `RobotStatePkg` 는 1,236바이트, 프레임 헤드 `0x5A5A`.
2026-08-08 에 이 방법으로 "캐시가 아니라 컨트롤러가 진짜 1 을 들고 있다"를 30초에 갈랐다.

⚠ **읽을 수 있는 안전 필드는 `EmergencyStop`·`safety_stop0/1_state`·`main_code`·`sub_code` 뿐이다.**
`alarmRebootRobot`(재기동 필요 플래그) 같은 건 상류 SDK 에만 있고 **배포본에는 없다** —
`archive/evidence-2026-07/2026-07-30/sdk-state-fields.md` §정정.

## 끌 때 — 순서를 지킨다

**순서를 어기면 데이터가 손상될 수 있다** (공식 설치 매뉴얼).

1. 실행 중인 프로그램·동작을 먼저 정지 (웹 화면의 STOP 또는 `/disarm`)
2. 상태 조회를 끊는다 — `POST /disconnect` (브리지는 켜 둬도 된다)
3. 펜던트/웹앱에서 로봇이 **"Stopped"** 로 보이는지 확인
4. 그다음에 컨트롤 박스 전원 OFF

우분투 PC 는 그냥 꺼도 된다 — 브리지는 systemd 가 다음 부팅에 다시 띄운다.
