# 핑거 교체 — 손끝이 움직이면 따라가야 하는 것들

분류: **SSOT**. 그리퍼 핑거를 다른 길이로 갈 때 이 순서대로 한다.
관련: `arch/STACK.md` §그리퍼 · `contract/PROGRAM-CONTRACT.md` §step · `runbook/WORKCELL-MEASURE.md` ·
`status/DECISION-LOG-CURRENT.md` D108

**왜 절차가 필요한가** — 핑거는 대환 공식 STEP 에도 없는 **고객 부품**이라 갈아 끼우는 것이
정상인데, 그 길이가 컨트롤러 툴 Z·3D 트윈·카메라 렌즈 높이·작업영역 판정에 **전부 올라타
있다.** 그리고 이 사건은 다른 변경과 성질이 다르다 — **툴 「번호」는 그대로다.** 번호만 보는
검사(좌표계 대조·`check_workspace` 의 frame 규칙)는 구조적으로 못 잡는다.

## 제일 위험한 자리 한 줄

지점은 **관절값으로 재생된다**(`MoveJ`). 그래서 핑거를 갈아도 팔 자세는 승인 때와 똑같고,
**손끝만 Δ(= 새 길이 − 25) 만큼 더 나간다.** 40mm 핑거로 갈면 승인된 하강이 15mm 더 깊어진다.
그 15mm 를 잡는 것은 `approvedWith.toolCoordMm` 하나뿐이다 (2026-08-11 에 세운 방어선).

## 값 미리보기 — 핑거 길이 L 하나가 정한다

| 값 | 식 | L=25 (지금) | L=40 | L=50 |
|---|---|---|---|---|
| 플랜지 → 핑거 끝 = **펜던트 툴 Z** | 110 + L | 135 | 150 | 160 |
| `gripper-mount.json` `toolLengthMm` | 110 + L | 135 | 150 | 160 |
| `depthCam.tcpYMm` (조립좌표계) | 38.02 + L | 63.02 | 78.02 | 88.02 |
| `depthCam.lensHeightMm` (TCP→렌즈) | 55 + L | 80 | 95 | 105 |
| 같은 관절값에서 손끝 이동량 | L − 25 | 0 | **−15** | **−25** |

**안 바뀌는 것** — `positionMm`·`toolAxisZMm`·`lensOffsetMm`(82)·브래킷/체결부 치수·
몸통 110mm. 브래킷은 **몸통**에 붙으므로 렌즈의 물리 위치는 그대로고, 바뀌는 것은
「TCP 에서 렌즈까지」라는 **기준 거리**뿐이다.

`.env` 의 `FR5_GRIPPER_FINGER_MM` 하나만 고치면 아래 셋은 `config.mjs` 가 계산한다.
**손으로 63.02·80 을 고치지 않는다** — 2026-08-11 이전에는 그 둘이 따로 박혀 있었다.

## 순서

### 1. 갈고 잰다 (물리)

핑거를 교체한 뒤 **몸통 끝 → 핑거 끝**을 줄자로 잰다. 플랜지에서 재지 않는다 —
몸통 110mm 는 이미 확정값이고, 두 번 재면 오차가 두 곳에서 들어온다.

### 2. 펜던트에서 툴 Z 를 고친다 — **여기서 옛 승인이 전부 깨진다**

활성 툴(`tool1`)의 Z 를 `110 + L` 로 고친다. 그리고 브리지가 같은 값을 읽는지 본다:

```bash
curl -s http://192.168.30.240:5055/state | python3 -m json.tool | grep -A3 coordDefs
```

⚠ **브리지를 재시작하고 읽는다.** `/state.coordDefs` 는 툴 **번호**로 캐시하므로, 번호가
그대로인 채 값만 바뀐 지금은 옛 값을 계속 내놓는다. (승인·실행 경로는 캐시를 안 타지만,
사람이 눈으로 확인하는 이 화면은 탄다.)

이 시점부터 승인된 슬롯은 실행이 막힌다 — **의도한 동작이다.** 사유에 `toolCoordMm` 이 뜬다.

### 3. `.env` 를 고치고 설정을 다시 굽는다

```bash
# .env — FR5_GRIPPER_FINGER_MM=<L>
node scripts/build/config.mjs
```

### 4. 핑거 STL 을 갈고 자산 게이트를 통과시킨다

새 핑거 STL 둘(`PGEA-100-40_finger_left/right.stl`)을 넣는다. 조립좌표계에서 **몸통 끝
Y=38.02 에 붙고 +Y 로 L 만큼 뻗어야** 한다.

```bash
bash scripts/check/assets.sh
```

- **길이 대조**가 STL 과 `.env` 를 맞춰 본다 (허용 0.05mm). 여기가 3번을 잊은 것을 잡는다
- **삼각형 수**가 틀리면 `WANT_GRIP_TRIS` 를 새 합계로 고친다 — 메시를 바꿨으니 정상이다.
  ⚠ 기준값을 고치는 것은 **길이 대조가 초록인 뒤에** 한다. 순서를 바꾸면 게이트 둘이 동시에
  빨간 상태에서 하나를 손으로 맞추게 되고, 그건 검사가 아니라 받아쓰기다

### 5. 시뮬 입력을 다시 굽는다

```bash
node scripts/dev/sim-fixture.mjs      # 실기에서 다시 받는다
```

`fr5-lab-a.json` 의 `coordDefs.tool` 과 `fkSamples` 가 **옛 툴로 잰 값**이라 통째로 무효다.
`fkSamples` 는 시뮬 기구학을 대조하는 유일한 실기 근거라 그대로 두면 대조가 거짓이 된다.

### 6. 작업영역은 **재측정이 아니라 확인**이다

상판·벽 값은 「로봇이 손끝으로 짚은 자리」다. 2번에서 툴 Z 를 **정확히** 고쳤다면 같은 물리
접촉점에서 같은 손끝 좌표가 나오므로 값이 그대로여야 한다. 그러니 5점을 다시 재지 말고
**한 점만 짚어 대조한다** (`WORKCELL-MEASURE.md` 의 절차 그대로, 상판 한 곳).

- 옛 값과 **±1mm 안**이면 통과. 툴 Z 가 맞았다는 뜻이다
- 어긋나면 **작업영역이 아니라 툴 Z 가 틀린 것이다.** 1번 실측으로 돌아간다 —
  여기서 작업영역 숫자를 고치면 틀린 툴 값 위에 보정을 얹는 꼴이고, 그 보정은
  자세가 바뀌면 안 맞는다 (D108 이 파지 중심을 툴에 안 박은 것과 같은 이유)

### 6-b. 손목 변환(hand-eye)은 **다시 잰다** — 계산으로 밀지 않는다 (2026-08-27 · D145)

작업영역과 반대다. **브래킷은 몸통에 붙어 안 움직이고 TCP 쪽이 내려간다**
(`arch/DEPTH-CAM.md` §80 은 핑거에 딸린 값이다). 그래서 `config.yaml` 의 `handEye.tMm[2]` 는
핑거를 Δ 만큼 늘리면 **정확히 Δ 만큼 틀린 값이 된다.**

크기 감각 — 08-13 실측 흩어짐이 **5.74mm** 이고 세워 꽂기의 좌우 여유는 **±10mm**(D122)다.
즉 **5mm 만 갈아도 캘리브레이션 한 번 분량의 오차**가 공짜로 얹히고, 10mm 면 여유를 다 먹는다.

⛔ **산술로 밀 수 있지만 밀지 않는다.** 핑거를 가는 김에 브래킷을 건드렸는지는 아무도 모르고,
자동으로 SSOT 를 덮는 경로는 이미 갭이 열려 있다 (계약 `VISION-CONTRACT.md` §hand-eye 유효성).
`scripts/robot/handeye-probe.py` 로 **다시 재고** 프로필을 사람이 고친다 — 물체를 안 움직인 채
자세를 **20° 이상 갈라** 2~3회 본다(그보다 작으면 흩어짐이 거짓으로 작게 나온다).

안 고치면 조용히 틀린다 — 화면의 손목 변환 줄은 `measuredAt` 을 그대로 초록으로 적는다.
**이 줄은 잰 날을 말하지 신선한지를 말하지 않는다.**

### 7. 슬롯을 다시 승인한다

2번에서 깨진 슬롯을 화면에서 **재승인**한다. 지점 자체는 관절값이라 다시 가르칠 필요가 없다 —
다만 **손끝이 Δ 만큼 내려간 자리로 간다는 것을 사람이 확인하고 승인하는 것**이 이 단계의 전부다.
접근·하강 높이를 쓰는 지점은 다시 가르치는 편이 낫다.

## 되돌리기

`.env` 의 `FR5_GRIPPER_FINGER_MM` 을 옛 값으로 되돌리고 `config.mjs` 를 다시 돌린다.
STL 은 git 이 들고 있다. **펜던트 툴 Z 는 자동으로 안 돌아온다** — 손으로 되돌린다.
슬롯 승인은 어느 방향이든 다시 받아야 한다.

## 이 절차가 기대는 방어선

| 무엇 | 어디 | 무엇을 잡나 |
|---|---|---|
| `approvedWith.toolCoordMm` | `FR5/bridge/slots.py` | 툴 값이 바뀐 채 옛 승인이 실행되는 것 |
| STL ↔ 설정 길이 대조 | `scripts/check/assets.sh` | STL 만 갈고 `.env` 를 잊은 것 |
| `--check` 드리프트 | `scripts/build/config.mjs` | `.env` 만 고치고 JSON 을 안 구운 것 |
| `fkSamples` 대조 | `scripts/check/sim-batch.sh` | 시뮬이 옛 툴 기준으로 도는 것 |

**툴 Z 를 안 고친 경우는 어느 게이트도 못 잡는다.** 로봇 안의 값이고 우리 코드에
`SetToolCoord` 호출이 0건이기 때문이다 (`GAP-MATRIX` §toolCoordId — 구현하면 터지는 자리라
일부러 안 넣었다). 2번의 되읽기 확인이 그 자리를 대신하는 유일한 장치다.
