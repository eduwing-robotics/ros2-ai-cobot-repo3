# LAYOUT-METRICS-CONTRACT — 맵·생산성 지표 계약

분류: **SSOT**. 맵 편집기(Dashboard)이 편집하고 AR 이 읽는 데이터, 그리고 팀원 알고리즘이
돌려주는 생산성 수치의 모양이다. **로봇 명령과 무관하다** — 로봇 쪽은 `API-CONTRACT.md`.

2026-08-04 에 `API-CONTRACT.md` 에서 이관했다 (그 문서가 상한을 넘었고, 두 주제는 소비자도
수명주기도 다르다). 내용은 그대로다.

## 목차

3개 절. **`##` 절과 이 목록은 같아야 한다** — `docs-weight.sh` 가 잰다.

- 맵 (맵 편집기가 편집하고 AR이 읽는다)
- 프로그램 슬롯 (P4) · 실행 기록 (P6) · 시연 (모방학습)
- 생산성 지표 — **우리가 요구 모양을 제시한다**

## 맵 (맵 편집기가 편집하고 AR이 읽는다)

새 목표(배치별 생산성 비교)의 데이터다. **모양의 정본은 `docs/ref/contract/SHARED-CORE.md`**이고
여기는 주고받는 방법만 정한다.

```
GET    /layouts             → [{ "id": "A", "name": "...", "verified": false }, ...]  // 목록만
GET    /layouts/{id}        → 맵 전문 (SHARED-CORE.md §모양)
PUT    /layouts/{id}        맵 전문. 없으면 만든다
DELETE /layouts/{id}
GET    /layouts/{id}/series → { source, cycleSec, series }   // 한 시퀀스의 타임라인 (해결된 결과)

GET    /scenarios           → [{ "id": "s1", "name": "조립 라인 · 49초" }, ...]  // 목록만
GET    /scenarios/{id}      → 시나리오 전문 (SHARED-CORE.md §1.7)
PUT    /scenarios/{id}      시나리오 전문. 없으면 만든다
DELETE /scenarios/{id}
```

- **`series` 는 맵 안에 넣지 않는다.** 같은 맵 위에 시간만 다른 실행이 여러 벌이고
  (F10 이 그걸 비교한다), 맵을 편집할 때마다 실행 기록이 딸려 오면 저장이 부풀어 오른다.
  모양의 정본은 `SHARED-CORE.md` §1.5

- **시나리오는 자기 id 를 가진 최상위 객체다** (2026-08-04). 맵은 `scenarioId` 로
  **가리키기만** 한다 — 가리키는 것은 데이터가 아니라서 위 규칙과 어긋나지 않는다.
  **맵 A·B 가 같은 `scenarioId` 를 가리킬 수 있다** — 그래야 같은 시퀀스를 두 배치에
  태워 시퀀스 타임을 진짜로 견준다(F8). 시나리오가 맵 소유였다면 복제본 둘이 갈라진다.

- **`GET /layouts/{id}/series` 는 남는다.** 화면은 "이 맵을 지금 무엇으로 돌리나" 만
  알면 되므로, 이 창구가 `scenarioId` → 저장분 → 프리셋 순으로 **해결한 결과**를 준다.
  화면이 해결 규칙을 알면 그 규칙이 화면마다 갈라진다.

- **단위는 mm·도(°)**다. 원점은 **실험실 바닥의 고정된 한 점**이고 로봇 베이스가 아니다.
  로봇 위치가 맵의 변수라서 그렇다 — 어기면 맵끼리 비교가 불가능해진다
- ⚠ **이 원점은 맵 도메인의 것이다.** 실기 좌표계는 둘 더 있다 — 아래 §원점은 하나가 아니다

### 원점은 하나가 아니다 (2026-08-07)

실기 좌표를 다루는 도메인이 셋이고 **원점이 다 다르다.** 모르고 숫자만 옮기면 1m 아래에 그린다.

| 원점 | 누가 쓰나 |
|---|---|
| **실험실 바닥 고정점** (SR_23) | 맵 · AR · 터틀봇 · 기록 노드 (`SHARED-CORE.md` §원점 규칙) |
| **상판 태그 id0** — z=0 이 **태그면**(바닥에서 ~1000mm 위) · 정의는 `calib-shots/tag-layout.json` | `global-cam.json` 의 `labToCam` · 글로벌 카메라 겹치기 전부 |
| **로봇 베이스** | `/state` · 작업영역 게이트 · 3D 화면 · `Shared/data/workcell.js` |

- **`labToCam` 의 "lab" 은 바닥이 아니다.** 태그가 로봇 카트 데크에 붙어 있어 z=0 이 바닥에서
  약 1000mm 위다. `extrinsics.py` 가 자기 산출물을 *"실험실 바닥 원점"* 이라 설명하던 문구는
  틀린 것이라 고쳤다 — 정본은 `tag-layout.json` 이 스스로 적는 정의다
- ⚠ **`/state.tcpMmDeg` 는 로봇 베이스가 아니라 사용자 좌표계 기준**이다. `coordDefs.user` 로
  환산해야 베이스가 된다 (D87 · `API-CONTRACT.md` §좌표계 정의). 이걸 몰라 하루를 잃었다
- **베이스 ↔ 태그 실측 등재** — `x 285 · y −179 · z 1.5 mm · yaw 177.1°(±1.2°)`, 파생
  `TCP 방위 = j1 + 7.8°`. 서로 독립인 근거 넷 + **줄자 검산 3.5mm(1.0%)**
  (`evidence/2026-08-07/robot-base-in-tag-frame.md`). **기계가 읽을 파일에는 아직 없다** —
  `global-cam.json` 은 생성물이라 손으로 못 쓴다 (`GAP-MATRIX`)
- ⛔ **바닥 ↔ 태그 는 상수로 적지 않는다.** 태그가 **이동식 카트** 데크에 있어 카트를 밀면
  바뀐다. 상수로 박으면 맵과 배치가 **조용히 갈라진다** — 어긋난 채 화면은 멀쩡해
  보이는, 제일 나쁜 실패 모양이다. 그때까지 배치는 태그 사각형에 맞추는 `?fit=` 로 산다
- **AR은 `GET`만 쓴다.** 폰에서 배치를 고치면 누가 무엇을 측정한 건지 알 수 없어진다
- 서버가 없는 동안은 **생성된 JSON을 빌드에 넣어** 읽기 전용으로 쓴다
  (`BUILD-VITE.md` §설정). 계약 모양은 지금 확정해 두고 저장소만 나중에 바꾼다

## 프로그램 슬롯 (P4) · 실행 기록 (P6) · 시연 (모방학습)

세 개가 같은 저장 경계를 쓴다. **저장 위치는 배포 트리 밖 `~/fr5-data/`** — 배포가
`rsync --delete` 라 트리 안에 두면 다음 배포 한 줄에 팀의 티칭 데이터가 사라진다 (D45).

```
GET/POST      /slots                 목록·생성(draft)
GET/PUT       /slots/{id}            리비전 추가 (불변 revisionId, 활성은 포인터)
POST          /slots/{id}/approve    { who, confirm: "현장확인" } → 실기 실행 자격
POST          /slots/{id}/run        { who } → approved 리비전만. 실행 전 재대조
GET           /history               명령·상태·차단 사유·승인 타임라인 (읽기)
```

- **승인 시점의 정체를 리비전에 고정 기록**하고, **실행 직전에 현재 세션과 다시 대조**한다 —
  robot profile · 펌웨어 문자열 · tool/user · 그리퍼 정체. 고정만 하고 안 보면 옛 승인이
  바뀐 실기에 그대로 나간다 (감사 P1)
- **재생은 실기 명령을 보내지 않는다.** History 재생은 타임라인 시각화이고, 위 허용목록
  때문에 구조적으로도 하드웨어에 닿지 않는다
- **중단 후 자동 재개는 없다.** 실행 기록에 마지막 완료 스텝을 남기고, 재개는 사람이 스텝을
  골라 명시적으로 시작한다 — 물체를 문 채 멈춘 상태에서 처음부터 돌리면 충돌이다 (감사 P1)
- **grip 단계는 성패를 판정한다** — 목표 대비 실측 개폐가 임계 밖이면 그 자리에서 정지.
  빈 그리퍼로 place 까지 진행하고 로그에 성공으로 남는 것을 막는다 (감사 P1)

### 모방학습 (신규 요구 · 2026-08-03 · D47 로 범위 확대)

그리퍼에 뎁스카메라를 달고 사람 시연을 수집해 **정책을 학습시키고 그 정책으로 작업을
수행한다.** 학습은 목적이자 수단이다 (D47). PRD 의 선은 여기까지다 — 로봇이 **배운 적 없는
작업을 스스로 계획**하는 것은 여전히 범위 밖이다.

```
POST /demos/start   { who, taskId }     시연 녹화 시작 (관절·그리퍼·카메라 동기 기록)
POST /demos/stop    { who }
GET  /demos         목록 (taskId 별 개수 — 30~50회가 학습 최소선)
POST /servo/start   { who, confirm: "현장확인" }   서보 스트리밍 구간 열기
WS   { "cmd": "servo", "jointsDeg": [...] }        주기적 목표 (8ms~50ms)
POST /servo/stop    { who }
```

- **서보 스트리밍은 별도 관문이다.** `MoveJ` 는 점 대 점이라 정책의 초당 수십 프레임을
  못 받는다. 게이트도 "명령당 5°" 가 아니라 **각속도(°/s)** 로 판정한다
  (`SAFETY-RULES.md` §서보 스트리밍 상한). `stop` 은 스트리밍 중에도 최우선이다
- **정책이 로봇을 직접 잡지 않는다.** 학습 도구(LeRobot 등)는 브리지에게 요청을 보내고,
  모든 프레임이 게이트를 통과한다. xmlrpc 는 연결이 하나뿐이라 예외를 만들 수 없다
- 시연 데이터(영상 포함)는 `~/fr5-data/demos/` — 용량 상한·보존기간을 촬영 **전에** 정한다.
  사람이 찍히므로 로봇 상태와 같은 공개 수준으로 두지 않는다
- 학습된 정책의 실행도 승인 관문을 탄다 — 사람이 검토하지 않은 궤적을 상한 안에서
  연속으로 흘려보내는 우회로를 열지 않는다
### 카메라 — 세 번째 관문이다 (D48 · **호스트 확정** D86)

**카메라는 자기 관문을 가진다.** 로봇 옆 FR5 브리지가 아니라, 카메라를 물은 기계 위에 작은
서버를 올린다. "장치 하나에 관문 하나" — tb-bridge·fr5-bridge 와 같은 패턴이다.

**호스트는 우분투 브리지 PC 직결이다** (2026-08-07 · D86) — `192.168.30.240:5058` ·
코드는 `Vision/bridge/`. USB **3.2 · 5000Mbps** 실측이 관문이었다. D61 이 후보 넷(손목 파이 /
팔 밑동 파이 / 우분투 직결 / PoE 파이)으로 보류했던 자리가 실물로 닫혔다.
⚠ 2026-08-08 정정 — 여기가 **D86 뒤에도 "미정" 이라고 적혀 있었다.** 계약이 이미 정해진 것을
미정이라 말하면 다음 사람이 고르라고 읽는다.

**그래도 계약은 호스트를 모르는 채로 쓴다** — 관문 주소만 약속하면 어느 기계에서 도는지는
배치도의 문제다. 아래 스키마는 호스트가 바뀌어도 그대로다. D86 이 *"착수를 막은 것은 D61 이
아니라 D61 을 읽은 방식이었다"* 고 적은 자리가 여기다.

```
GET  /api/camera/info          { model, serial, firmware, usb, calibId, depthIntrinsics, colorIntrinsics }
GET  /api/camera/state         아래 스키마 — ★ 제안 판정이 이걸 읽는다
GET  /api/camera/preview       압축 컬러 (화면 확인용 · 저해상도)
GET  /api/camera/depth/frame   깊이 **1회 스냅샷** — 16비트 PNG · 밀리미터 (아래 §깊이 스냅샷)
GET  /api/camera/rgbd/frame    **같은 촬영 묶음** — 컬러에 정렬된 깊이+컬러 ZIP (아래 §RGB·뎁스 묶음)
GET  /api/camera/ir/frame      **적외선 원본 1회** — 8비트 PNG (아래 §적외선 원본 · `?which=1|2`)
POST /api/camera/measure       깊이 1회 측정 → { pose, depthValid, measuredAt }
GET  /api/camera/frames?from=  시연 구간의 프레임 메타 (경로·촬영시각)
POST /api/camera/record/start  { taskId, demoId }   ← 브리지가 시연 시작 때 부른다
POST /api/camera/record/stop
```

```jsonc
// GET /api/camera/state
{
  "t": 1785329668.42,
  "cameraId": "wrist-d435",
  "connected": true,
  "usb": "2.1",                  // 2.1 이면 고 fps 모드가 잘린다 (DEPTH-CAM.md §USB)
  "depth": {
    "resolution": "848x480",
    "fps": 10,
    "minZmm": 195,               // ★ 현재 해상도의 Min-Z (DEPTH-CAM.md 표)
    "valid": true,               // ★ 지금 사각지대 밖인가
    "validRatio": 0.241,         // ★ 프레임 전체 유효 픽셀 비율
    "validRatioCenter": 0.076,   // ★ 중앙 1/3 의 유효 비율 — 물건이 놓이는 곳이다
    "validReason": null,         // `valid:false` 일 때만 사유. 아래 §사유
    "tuningNotes": []            // 깊이 노브를 **못 건** 사유. 빈 배열이 정상 (2026-08-11 신설)
  },
  "lastFrameAt": 1785329668.31,  // 카메라가 **찍은** 시각. 도착 시각이 아니다
  "clock": "bridge",             // 이 시각이 어느 시계 기준인가
  "clockSkewMs": 0,              // 브리지 시계와의 차이. 못 재면 null 이 아니라 fail-closed
  "tempC": 41.2
}
```

- **`minZmm` 과 `valid` 는 서버가 싣는다** (2026-08-04 신설). 깊이 사각지대 판정을 비전 쪽
  양심에 맡기지 않는다 — "클라이언트를 믿지 않는다"를 깊이에도 적용한다. 사각지대 안의
  깊이는 **틀린 값이 아니라 없는 값**이고, 그걸 모르고 뱉은 좌표는 그럴듯해 보인다.
  `API-CONTRACT.md` §제안이 이 필드들을 읽어 `depthInvalid` 로 거부한다
- **유효는 불리언이 아니라 비율이다** (2026-08-05 실측). 손끝을 바닥에 댄 자세에서 424×240 이
  전체 24.1% · **중앙 7.6%** 를 줬다 — `valid: true` 하나로는 이걸 99% 와 구분하지 못한다.
  **판정은 `validRatioCenter` 로 한다.** 임계값은 실측 후 정하고, 그전까지 fail-closed.
- ⛔ **`validRatioCenter` 는 「물체가 보인다」를 보장하지 않는다** (2026-08-11 실측 · 신설).
  이 절이 `validRatioCenter` 를 *"물건이 놓이는 곳"* 이라 적었는데 **물건은 바닥보다 카메라에
  가깝다** — 그래서 **물체가 바닥보다 먼저 Min-Z 를 깬다.** 실측: 640×360(Min-Z 150)에서
  바닥 148mm 가 `validRatio 30.4%` 로 살아 있는데 그 위 11mm 에 솟은 총알(꼭대기 137mm)은
  **화소 0** 이었다. 판정은 통과인데 **볼 것을 못 본 상태**다.
  **그래서 물체를 재는 자리에서는 여유를 물체 높이만큼 더 잡는다** — 필요 Min-Z 는
  `바닥거리`가 아니라 **`바닥거리 − 물체높이`** 로 고른다. 근거
  `evidence/2026-08-11/round-detect-probe.md` · 계기 `scripts/robot/depth-probe.py`
- **`tuningNotes` 는 「설정대로 안 돌고 있다」를 말한다** (2026-08-11 신설). `config.yaml` §tuning 의
  노브(레이저·프리셋·depth_units·disparity_shift)를 못 걸면 사유가 여기 쌓인다. **빈 배열이
  정상**이고, 차 있으면 그 세션의 깊이는 설정대로가 아니다 — 조용히 실패한 튜닝은
  "왜 이 세션만 깊이가 나쁜가" 로 돌아온다. 등재·범위는 `arch/STACK.md` §깊이 노브.
- **`validReason` 은 `false` 의 이유를 가른다** (2026-08-07 신설). 판정은 `valid` 하나로 하되,
  화면은 이걸 읽어 **고칠 수 있는 것과 없는 것**을 가른다. 넷뿐이다 —
  `noCamera`(장치 없음) · `noFrame`(프레임이 낡음) · `thresholdUnset`(임계값 미실측) ·
  `belowThreshold`(진짜 사각지대). **`thresholdUnset` 을 `belowThreshold` 와 같은 얼굴로 띄우면
  안 된다** — 고칠 수 없는 경고를 상주시키면 사람이 경고를 무시하는 법을 배운다
  (2026-08-07 `설정 미확인` 과 같은 자리). `valid:true` 면 `null` 이다.
- **무효는 0 만이 아니다** — Z 가 **65535 로 포화된 쓰레기 픽셀**이 섞여 나온다. "0 이 아니면
  유효"로 세면 통과한다. 서버가 `minZmm`~상한(기본 4000mm) 밖을 **버린 뒤** 비율을 낸다
- **해상도는 두 모드를 오간다** — 접근 848×480 / 근접 480×270(USB2)·424×240(USB3).
  전환에는 스트림 재구성이 걸리므로 **전환 중에는 `valid: false`** 로 둔다
- **못 읽으면 아무 일도 안 일어난다** — `/api/camera/state` 가 무응답이거나 `lastFrameAt` 이
  낡으면 제안이 전부 거부된다 (fail-closed · `SAFETY-RULES.md` 제1원칙)

- **카메라 관문은 로봇에 명령하지 않는다.** 찍고·시각 찍고·저장할 뿐이다. 실행 여부는 언제나
  FR5 브리지의 안전 게이트가 정한다 (`Vision/AGENTS.md` §제안만 만든다)
- **원본 깊이를 실시간으로 흘리지 않는다.** 관문이 로컬에 먼저 쓰고 나중에 동기화한다.
  실시간 **스트림** 경로는 압축 컬러(화면 확인·정책 입력)뿐이다 — 그래서 **무선으로도 충분하다**

#### 깊이 스냅샷 — `GET /api/camera/depth/frame` (2026-08-11 신설)

**왜 열었나** — 컬러 단독 분할이 이 작업물에서 실패하는 것을 실측으로 확인했다
(`evidence/2026-08-11/round-detect-probe.md` · 황동일 땐 정반사 하이라이트만, 무광 처리 뒤엔
그림자가 물체와 뭉쳐 종횡비가 +154% / −48% 로 양쪽 다 틀렸다). **밝기는 기하가 아니다.**
검출을 깊이로 옮기려면 깊이 값을 볼 수 있어야 하는데 관문이 비율 두 개로만 요약해 내보내고
있었다 — **판정할 수 없는 상태였다.**

- **단발이다. 스트림이 아니다.** 위 §원본 깊이 규약은 그대로다 — 연속 경로는 여전히 압축
  컬러뿐이다. 이건 검출 개발·진단용으로 **한 장을 달라고 할 때** 주는 것이다. 호스트가
  유선 직결로 확정돼(D86) 무선 대역 전제가 약해졌지만, 그것이 스트림을 여는 근거는 아니다
- **밀리미터 정수 · 무효는 `0`.** `minZmm`~상한(기본 4000mm) 밖은 — 포화 65535 를 포함해 —
  **서버가 0 으로 비운 뒤** 낸다. 비율을 낼 때 쓰는 규칙(§무효는 0 만이 아니다)과 **같은
  규칙을 같은 곳에서** 적용한다. 소비처가 판정을 다시 지으면 두 판정이 갈린다 (D103)
- **컬러와 정렬돼 있지 않다.** 이 깊이 단독 라우트는 기존 계약을 유지한다. 컬러 화소와
  짝지어야 하는 소비자는 아래 `/rgbd/frame` 한 묶음을 써야 한다
- **`pose` 를 안 낸다.** 그래서 hand-eye 를 안 기다린다 — `measure` 가 못 열리는 이유
  (§낼 수 없는 필드를 `null` 로 채우지 않는다)가 여기엔 안 걸린다
- **낡으면 503.** `preview` 와 같은 규약이다 — 옛 프레임을 200 으로 주지 않는다
- 해상도는 `/state` 의 `depth.resolution` 과 같다. 따로 싣지 않는다 — 두 곳에 적으면 갈린다
- **타임스탬프는 도착 시각이 아니라 촬영 시각**을 관문이 직접 찍는다. 도착 시각으로 찍으면
  무선 지터가 데이터에 섞여 학습이 틀린 짝을 배운다. 시계는 랜 안에서 동기(NTP)하고
  **짝짓기 기준은 FR5 브리지의 시계 하나**다
- 프레임은 `calibId` 로 그때의 캘리브레이션을 가리킨다 — 카메라를 옮기면 값이 바뀌므로
  옛 시연을 살리려면 이 참조가 필요하다

#### RGB·뎁스 묶음 — `GET /api/camera/rgbd/frame` (2026-09-09 신설)

총알처럼 컬러에서는 보이지만 깊이가 빠지는 물체의 xy를 3차원으로 옮기는 단발 스냅샷이다.
RealSense의 같은 frameset에서 **깊이를 컬러 화소계에** 정렬한 뒤 아래 세 파일을 ZIP 하나로 낸다.
반대로 컬러를 깊이에 맞추면 깊이가 빈 총알 화소의 컬러도 검게 사라지므로 쓰지 않는다.

- `manifest.json` — `{ t, alignment:"depthToColor", widthPx, heightPx, depthUnit:"mm", calibId, intrinsics, colorToDepth }`
- `color.jpg` — 전체 해상도 컬러
- `depth.png` — 같은 묶음의 16비트 밀리미터 깊이. 무효값은 기존처럼 0

세 파일은 **같은 응답 안의 한 묶음**이다. `/preview`와 `/depth/frame`을 따로 불러 시간으로
짝짓지 않는다. 둘 중 하나가 없거나 모양이 다르거나 1초보다 낡으면 503이며, 소비자는 검출을
차단한다. `intrinsics`는 컬러 화소계의 장치 실측값이고 소비자는 이것으로 역투영한다.
그 점은 아직 컬러 렌즈 원점 기준이므로 `colorToDepth:{rotationRowMajor[9],translationMm[3]}`로 깊이
렌즈 좌표로 옮긴 뒤 기존 hand-eye 변환에 넣는다. 이 변환을 생략하지 않는다.
`/preview`는 사람 확인용 기존 화각을 유지하고 `/depth/frame`도 호환성을 위해 그대로 둔다.

### `depthIntrinsics` — **장치가 정본이다** (2026-08-27)

`{ widthPx, heightPx, fx, fy, ppx, ppy, model, coeffs }` 또는 `null`.

⛔ **소비처가 화각에서 유도하지 않는다.** 그전에는 `DEPTH-CAM.md` §화각(89.74°/58.79°)에서
`fx = (W/2)/tan(HFOV/2)` 로 뽑아 썼는데, **주점이 3~7화소 틀렸다** — `cx 424 vs 427.0` ·
`cy 240 vs 247.3`. 220mm 거리에서 1.5~3.8mm 다. 그리고 해상도를 바꾸면 통째로 다시 적어야 했다.

⛔ **못 읽으면 `null`** — 지어내지 않는다. 소비처는 `null` 을 「좌표를 못 낸다」로 읽는다.

### 적외선 원본 — **깊이가 실패한 자리를 보는 창** (2026-08-27 · D151)

스테레오 두 이미저의 **원본 흑백**이다. 깊이는 이 둘을 매칭해 만들어지므로, **깊이가 비면
둘 중 하나가 안 보였거나 매칭이 실패한 것**이다. 원본을 보면 그 둘이 갈린다.

⛔ **왜 필요했나** — 08-27 에 세워 꽂힌 총알 넷 중 **둘이 깊이에 아예 없었다**(60px 안에
총알대 화소 0). 그런데 원인이 둘로 갈렸고 **깊이만 봐서는 못 가른다**:

| 후보 | 원본에서 보이는 것 |
|---|---|
| **가림** — 그리퍼가 자기 시야를 먹는다(렌즈가 툴 축에서 82mm 옆) | 총알이 **안 보인다** |
| **매칭 실패** — 황동이 반짝여 스테레오가 못 푼다 | 총알이 **또렷이 보인다** |

- **단발이다. 스트림이 아니다.** `depth/frame` 과 같은 규약 — 진단·검출 개발용으로 한 장을 준다
- **낡으면 503** — 옛 프레임을 200 으로 주지 않는다
- `?which=1`(왼쪽 · 기본) · `?which=2`(오른쪽). **깊이의 원점은 왼쪽 이미저**라 기본이 1 이다
- ⛔ **깊이와 정렬돼 있다** — 같은 이미저·같은 해상도다. 컬러와는 아니다(`rs.align` 이 선행)
- ⛔ **판정에 안 쓴다.** 유효율은 여전히 **깊이 원본**이 낸다 — 여기는 사람이 보고 원인을
  가르는 창이지 게이트 입력이 아니다

### ⛔ `calibId` 는 **프레임 출처 참조 하나**다 — 손목 변환 배지가 아니다 (2026-08-27 · D145)

두 뜻을 겸하고 있었다. 계약은 위처럼 **「이 프레임이 어느 캘리브레이션에서 나왔나」**로
썼는데, 화면(`depth-state.js`)이 **「hand-eye 가 검증됐나」**로 읽어 `null` 일 때
「좌표 제안 불가」를 띄웠다. 한 필드가 두 뜻이면 한쪽을 고칠 때 다른 쪽이 조용히 틀어진다.

| 묻는 것 | 정본 | 내는 곳 |
|---|---|---|
| 이 프레임은 어느 캘리브에서 나왔나 | **관문의 장치 동일성** | `GET /api/camera/info` 의 `calibId` |
| 카메라 좌표를 로봇 좌표로 옮길 수 있나 | **프로필 `handEye`** | FR5 브리지 `GET /state` 의 `handEye` |

**관문은 `calibId` 를 스스로 만든다** — `d435-<serial>-fw<firmware>` 처럼 자기가 이미 아는
값으로 짓는다. 관문은 FR5 브리지의 `config.yaml` 을 **읽지 않는다**(별 프로세스·별 포트).
읽게 만들면 배포가 파일 하나를 빠뜨렸을 때 조용히 죽는 면이 하나 더 생긴다.

⚠ **그래서 `calibId` 가 있어도 좌표 제안이 된다는 뜻이 아니다.** 장치가 그대로라는 뜻뿐이다.

## 생산성 지표 — **우리가 요구 모양을 제시한다**

**수치는 팀원 알고리즘이 만든다. 우리는 받아서 보여준다** (`ARCHITECTURE.md` §우리 몫).
그래서 계약을 기다리지 않는다 — **화면을 가진 쪽이 필요한 모양을 먼저 낸다.**

### 요구 모양 (맵 1개의 실행 결과)

```jsonc
{
  "layoutId": "A",
  "source": "sim",              // sim | measured | mock — 화면에 출처를 표시한다
  "cycles": 120,                // 처리한 개수
  "durationSec": 3600,
  "metrics": {
    "throughputPerHour": 120.0,                       // 필수
    "cycleTimeSec": { "mean": 30.0, "p50": 29.1, "p95": 38.4 },  // mean 필수
    "amrTravelMm":   480000,                          // 선택
    "waitSec":       { "arm": 220, "amr": 640 },      // 선택
    "interferences": 3                                // 선택
  },
  "series": [ { "tSec": 0.0, "event": "pick", "station": "in" } ]   // 선택 — 타임라인용
}
```

**필수는 둘뿐이다** — `throughputPerHour`와 `cycleTimeSec.mean`.
나머지는 선택이고, **없으면 그 칸만 "—"로 비운다.** 화면이 깨지지 않는다.

이렇게 나눈 이유: 팀원이 처리량 하나만 내도 **비교 화면이 그날 동작한다.**
전부 갖춰질 때까지 기다리면 우리 쪽 진행이 팀원 일정에 묶인다.

### 지금은 목업으로 만든다

```
Shared/data/datasource/mock.js    손으로 만든 JSON 두 개 (맵 A · B)
Shared/data/datasource/http.js    나중에 이 파일만 바꿔 끼운다
```

**화면은 어느 쪽인지 모른다.** 목업→실물 교체가 파일 한 개여야 한다
(`ARCHITECTURE.md` §확장성).

### 팀원과 맞춰야 할 것 넷

우리가 위 모양을 제시하고, 아래만 회신받으면 `http.js`를 짤 수 있다.

| # | 물어볼 것 | 우리 기본값 |
|---|---|---|
| 1 | 이 모양으로 줄 수 있나. 못 주는 필드가 있나 | 필수 둘만 있으면 된다 |
| 2 | 어떻게 전달하나 — HTTP / 파일 / 데이터베이스 | 우선 **JSON 파일**로 받아도 된다 |
| 3 | **한 시퀀스의 정의** — 무엇을 하면 1개 처리인가 | 처리량의 분모라 반드시 합의해야 한다 |
| 4 | 실행이 오래 걸리나 (동기/비동기) | 동기라고 가정. 오래 걸리면 작업 ID를 추가한다 |

3번만 어긋나도 **두 맵의 처리량을 비교할 수 없다.** 나머지 셋은 나중에 바꿔도 된다.

정해지면 이 절을 확정 계약으로 고치고 `DECISION-LOG`에 한 줄 남긴다.
