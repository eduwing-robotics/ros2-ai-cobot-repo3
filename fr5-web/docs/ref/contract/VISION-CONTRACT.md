## 제안 — `POST /proposal` (2026-08-04 · D61)

**비전은 명령을 만들지 않는다. 제안을 만든다.** 비전값이 곧바로 명령이 되면 하드 룰 3
(사람 확인 없이 큰 동작 금지)과 정면으로 부딪힌다.

### 제안은 실기 명령이 아니다 — 승인되면 **번역**된다

**§명령의 허용목록(`jog`·`moveJ`·`gripper`·`stop`)은 그대로다.** `proposal` 은 그 목록에
새 이름을 더하지 않는다. 승인된 제안은 브리지가 `moveJ`·`gripper` 로 **번역**해서
**같은 게이트를 처음부터 다시 태운다.** 비전 전용 실행 경로를 만들지 않는다 — 만드는 순간
안전 게이트를 우회하는 두 번째 문이 생긴다 (감사 P1 원칙 유지).

```text
POST /proposal                       → { proposalId, verdict, reason, expiresAt }
GET  /proposals                      → 대기 목록 (화면이 고스트로 그린다)
POST /proposal/{id}/approve  { who, token }   → 여기서 moveJ·gripper 로 번역된다
POST /proposal/{id}/reject   { who, token }
```

```jsonc
// POST /proposal — 비전이 보내는 것
{
  "kind": "grasp",                    // grasp | align | retighten
  "source": "vision",
  "targetPose": { "tcpMmDeg": [412.5, -88.0, 210.3, 180, 0, 45] },   // mm · 도(°)

  "measuredAt": 1785329668.31,        // 촬영 시각 (§카메라 규약)
  "anchorPose": { "jointsDeg": [...], "tcpMmDeg": [...] },   // ★ 잴 때 로봇이 있던 자세
  "validUntil": 1785329698.31,        // 이 시각 넘으면 무효

  "depthValidAtMeasure": true,        // ★ 사각지대 밖에서 쟀나
  "minZmmAtMeasure": 195,
  "toolId": 0, "userId": 0,           // 잴 때의 좌표계
  "confidence": 0.87
}
```

```jsonc
// 응답
{ "proposalId": "p-7f3a",
  "verdict": "needsHumanConfirm",     // auto | needsHumanConfirm | rejected
  "reason": null,
  "expiresAt": 1785329698.31 }
```

### 판정은 3단이다

| verdict | 언제 | 그다음 |
|---|---|---|
| `auto` | 상한 안의 **작은 보정**만 | 바로 번역·실행 |
| `needsHumanConfirm` | 그 밖의 정상 제안 | 화면에 고스트로 뜨고 **사람이 누른다** |
| `rejected` | 사유와 함께 거부 | **아무 일도 안 일어난다** |

✅ **2026-09-07 저녁 구현됨** (사다리 7 · `FR5/bridge/main.py` §제안) — 본문에 **`jointsDeg[6]`** 를 함께 받는다(화면이 `/ik` 로 푼 해 · 참조 해가 갈리지 않게). `targetPose` 는 기록용. 판정은 `/ik` 와 같은 `cmds.motion(dry_run)` 경로 훑기, 승인은 `owner_gate`+ARMED+수명 90초 → `moveJ` 번역(속도 상한 10%). 요약 표는 `API-CONTRACT.md` §제안 요약.

⚠ **지금은 `auto` 를 열지 않는다.** 전부 `needsHumanConfirm` 이다. 자동 통과는 실기 데이터가
쌓여 상한을 실측으로 정한 뒤에 연다. 여는 것은 나중에 쉽고, 닫는 것은 사고 뒤다.

거부 사유(`reason`)는 최소 이만큼을 구분한다 — `expired` · `depthInvalid` · `staleAnchor` ·
`outOfReach` · `overLimit` · `noOwner` · `notArmed` · `inDragTeach`(조건 25) ·
`toolFrameMismatch`(아래 §대신 남는 게이트 · 옛 이름 `toolCalibrationUnverified` → `tcpDatumUndecided`) ·
`cameraStale`.

**상한 값을 새로 만들지 않는다.** §안전 규칙과 `SAFETY-RULES.md` §상한을 그대로 쓴다.
비전용 상한을 따로 두면 그게 우회로가 된다.

### 못 박는 것 다섯

1. **`/proposal` 은 로봇을 움직이지 않는다.** 접수하고 판정만 반환한다. 실행은 `approve` 다.
   접수와 실행을 한 호출로 합치면 "제안"이라는 말이 거짓말이 된다
2. **`validUntil` 은 두 번 검사한다** — 접수할 때, 그리고 **번역·실행 직전 한 번 더.**
   승인 대기 중에 만료될 수 있다. 마지막 구간은 깊이가 없어(§카메라 · Min-Z) 이게 유일한
   방어선이다
3. **`anchorPose` 가 없으면 좌표가 틀린다.** hand-eye 가 손목 기준이라 실행 시점 자세가
   잴 때와 다르면 변환이 달라진다. 허용 반경을 벗어나면 `staleAnchor` 로 거부한다
4. **조종권은 접수가 아니라 승인에 건다.** 제안 접수는 토큰이 필요 없다(안전하니까).
   **`approve`·`reject` 는 토큰 필수** — 거기가 제안이 움직임으로 바뀌는 지점이다 (D55)
5. **제안·판정·승인·실행을 전부 기록한다.** 나중에 "왜 움직였나" 에 답해야 한다

### 제한 실행 S0~S4 — 지정한 안전점에서 멈춘다 (2026-09-10)

실기 마법사는 `AUTOMATIC-SEQUENCE-STAGE-GATES.md`의 안전 단계 중 **S0~S4만** 제한
실행으로 연다. 사람이 `마지막 단계`와 `현장확인`을 고정한 뒤 `자동 작업 시작`을 한 번
누르면, 그 승인은 지정 단계까지의 관측 이동에만 유효하다.

- S0 상태 확인과 S1 글로벌 검출은 읽기 전용이다.
- S2는 자세 A 이동·도착 확인·뎁스 스캔과 최대 3패스 재중심만 한다. 각 정지 관측 자세에서
  `/scan`이 거치대 후보를 정확히 하나로 못 좁히면 같은 자세에서 최대 3회 재촬영하고, 첫 유효
  프레임만 채택한다. 세 번 모두 결측이면 실패하며 자세를 더 내리거나 이전 프레임을 쓰지 않는다.
  첫 300mm 관측에서
  `carrier` 총알이 기대 수보다 적으면, 깊이가 찾은 중심 xy와 대강값의 윗면 z를 합쳐 **최대
  4개의 제한된 총알 탐색 자세**를 차례로 시도한다. 후보는 `250mm·같은 손목각 →
  225mm·같은 손목각 → 250mm·손목 +90° → 250mm·손목 -90°`다. 225mm는 D435 Min-Z
  195mm보다 30mm 높은 하한이고, ±90°는 카메라 광축 둘레만 돌려 스테레오 그림자 방향을
  바꾼다. 각 후보는 `/ik`와 안전 게이트가 통과한 경우에만 기존 경로 제안·도착 확인으로 이동하며,
  정지 뒤 최대 3회 재촬영하고 기대 총알 수가 채워지는 즉시 탐색을 끝낸다. IK·게이트가 거부한
  후보는 장부에 남기고 건너뛰며, 이동·도착 확인이 실패하거나 카메라가 유효한 거치대 프레임을
  못 내면 더 움직이지 않고 실패한다. 4후보 뒤에도 부족하면 S2를 완료로 올리지 않는다.
  이는 관측 거리와 카메라 광축 둘레 손목각만 바꾸는 것이며 파지 하강·그리퍼 동작은 아니다.
  무한 재시도하지 않고 **최대 4회 이동·12회 정지 재촬영**에서 멈춘다. 각 이동은 기존
  `/proposal → needsHumanConfirm → approve`를 그대로 타고, 승인 직전에 owner·ARMED·수명과
  조건 1~27을 다시 검사한다. 이 `approve`는 사용자가 시작 전에 현장확인하고 누른 제한 실행 한 건의
  범위 안에서 실행기가 이어 호출하며, 후보마다 버튼을 다시 요구하지 않는다. `auto` verdict를 열거나
  새 실행 엔드포인트를 만들지 않는다.
- S3는 IK·접촉·안전 게이트·총알 간섭을 계산만 하고 **HOLD**한다. 집기 접근, 하강,
  그리퍼, 터틀봇 명령은 이 제한 실행에 없다.
- S3R을 시작 전에 명시한 실행은 S2와 긴 벽 4후보 판정을 이어받아, **미래 터틀봇 정차·놓기
  전체 계획을 요구하지 않고** 현재 자세→선택한 긴 벽 중앙의 높은 접근 자세만 독립적으로
  IK·접촉·안전 게이트 검사한다. 통과하면 그 높이에서 그리퍼 `100% → 60%(24mm)` readback을
  확인한 뒤 HOLD한다. S3R 완료
  목록에 S3를 넣지 않으며 `grasp` 하강, `close` 4%, 들기,
  터틀봇 명령은 없다. S3 승인은 S3R로, S3R 승인은 S3 전체 계획으로 자동 승격되지 않는다.
- S4는 `approach`·`pregrip`·`grasp`·`close`·`lift`의 IK·안전 게이트·접촉과 총알 간섭을
  **전부 먼저** 통과시킨다. 낮은 `grasp` 고스트를 세운 `PREVIEW`에서는 실기 명령을 하나도
  보내지 않으며, 사람이 `고스트 확인 · 집기 실행`을 누른 뒤에만 다섯 칸을 기존 제안·승인·도착
  확인 경로로 직렬 실행한다. `grasp`나 `close`에서 계획된 HOLD를 만들지 않고 `lift`에서 끝낸다.
  터틀봇·운반·놓기 명령은 이 상한에 없다.
- 시작 때마다 새 runId를 만들고 `requestedLimit`·현장 상태·각 제안 ID와 승인 결과를 같은
  장부에 기록한다. 이전 마법사 runId·cursor·조준값은 자동 실행의 근거로 복원하지 않는다.
- 실행 중 상한을 늘릴 수 없다. 새로고침·WebSocket 재접속·브리지 재시작·조종권 상실·
  DISARM이면 남은 승인은 폐기하고 자동 재개하지 않는다.
- 재촬영 상한 뒤 검출 결측, 제안 거부·만료, 도착 시간초과, 계획 빨강 중 하나라도 나오면 실패로 끝내고
  다음 제안을 만들지 않는다. 모션 응답이 불확실할 때 같은 제안을 자동 재전송하지 않는다.

S5 이후는 닫혀 있다. 정확한 터틀봇 정차·놓기 계획은 거치대를 안전 높이까지 든 뒤 새 터틀봇
pose로 S5에서 푼다. S4의 실기 승격은 공중 리허설 뒤 집기 3/3을 요구하며, 그 전에는 고스트
미리보기와 목업 검증만 증거가 된다. 각 단계의 목업 실패 주입·실기 3회·회귀 게이트가 통과하고
사람이 다음 상한을 명시한 뒤에만 이 계약을 한 단계씩 확장한다.

## 추종 — 안전 높이를 유지하며 **따라만 간다** (2026-08-13 · D132)

**`auto` 를 여는 첫 사례다.** §판정 3단이 *"지금은 `auto` 를 열지 않는다"* 라고 적어 둔 그
문을 **추종에 한해** 연다. 근거는 하나 — **추종은 파지가 아니다.** 안전 거리를 유지하므로
물체에도 받침에도 닿지 않고, 그래서 「큰 동작」이지만 「닿는 동작」이 아니다.

⛔ **그래도 사람이 근처에 있으면 위험하다.** 우리에게 사람을 보는 인증된 층은 없다
(`GOAL-cam-person-watch` §⛔). 그래서 아래 조건 전부를 **동시에** 요구한다.

### 창구 — 켜기·끄기·상태 (2026-08-28 신설)

```
POST /follow/on   { who, token, confirm: "현장확인" }  → { ok, follow, reasons }
POST /follow/off  { who, token }                       → { ok, follow }
GET  /state       → follow: { on, who, secondsLeft, reason }
```

- **`confirm: "현장확인"` 을 요구한다** — `/arm` 과 같은 문구다. 조건 1(사람이 켠다)은
  버튼 한 번으로는 안 지켜진다. 「사람이 곁에 있음」을 말로 적게 한다
- **조종권 · `ARMED` 를 요구한다** (조건 2). 둘 중 하나만 있어도 거부다
- **끄기는 조종권만** 요구한다 — 끄는 길은 켜는 길보다 항상 넓어야 한다
- **`/state.follow` 는 꺼져 있을 때도 나온다** (조건 7) — 마지막 사유를 들고 있어야
  화면이 「왜 안 도나」에 답한다. 조용히 사라지면 사람이 못 묻는다
#### `POST /follow/step` — **한 번만 간다** (2026-09-04 신설)

```
POST /follow/step { who, token, confirm: "현장확인" }
                  → { ok, goal: {tcpMmDeg, jointsDeg}, target, reasons }
```

**연속 추종보다 먼저 놓는 칸이다.** 「켜 두면 알아서 따라간다」는 사람이 안 누르는 동안에도
움직이므로, 데드밴드·자동꺼짐·정지가 **전부 처음부터 실기에서 시험된다.** 한 번만 가는
쪽은 사람이 누를 때만 움직여서 **지켜보기 쉽고, 게이트·속도·정지를 한 번에 검증**한다.

⭐ **조건 1(사람이 명시적으로 켠다)을 스위치 없이 만족한다** — 한 번 가는 것은 **매번
사람이 켜는 것과 같기 때문**이다. 그래서 `follow_switch` 를 안 보고 `autoOffAfterS` 도
뜻이 없다(켠 채로 남는 상태가 없다). 나머지 조건 2·3·4·5·6 은 **그대로 전부** 요구한다.

⛔ **비전 전용 실행 경로를 만들지 않는다.** 목표는 `moveJ` 로 번역돼 `commands.motion` 의
**같은 게이트**를 탄다 — `POST /ik` 가 `dry_run` 으로 타는 바로 그 함수다. 그래서
「미리보기는 통과인데 실제로는 거부」가 구조적으로 안 생긴다.

평행 그리퍼로 안전 높이에서 따라만 가는 동안에는 TCP `rz`와 `rz±180°`가 같은 도구 형상이다.
두 자세를 현재 관절을 참조한 IK로 모두 풀고, **각 후보의 실제 관절값을 그대로** 경로·정착
게이트에 태운 뒤 통과 후보 중 최대 관절 변화가 작은 하나를 고른다. 관절 j1·j5·j6의 한계는
±175°이므로 `+151°→-162°`를 단순 래핑해 47°라고 속이지 않는다. 동치 TCP를 다시 풀어
한계 안의 별도 해를 얻지 못하면 기존처럼 거부한다. 미리보기와 `/follow/step`은 같은 두 후보와
같은 선택 순서를 써야 하며, 실행 응답의 `goal.tcpMmDeg`·`goal.jointsDeg`는 실제 선택값이다.

⛔ 데드밴드는 **마지막으로 보낸 추종 목표가 아니라 최신 실제 TCP readback**과 새 목표를
비교한다. 추종 사이에 출발 조준·지점 이동 같은 다른 창구가 팔을 옮길 수 있어서, 옛 추종 목표를
기준으로 삼으면 실제 팔이 멀리 있어도 `moved:false`로 잘못 건너뛴다. 실제 TCP가 새 목표의
`releaseMm` 안에 있을 때만 같은 자리를 다시 가지 않는다.

- ⛔ **`on` 이 되었다고 움직이는 것이 아니다.** 매 틱 조건 3·4·5 를 다시 본다 —
  특히 **조건 5(표적을 지금 보고 있다)** 는 비전이 좌표를 줄 때만 참이다.
  검출기가 없으면 `on` 인 채로 **아무것도 안 움직이고 사유만 낸다.** 그게 옳다

### 무엇을 따라가나 — **표적도 프로필이 정한다** (2026-09-04)

추종은 터틀봇을 따라가려고 만들었고 표적 태그 번호가 **코드에 박혀 있었다**(`AMR_TAG_ID = 18`).
그런데 첫 실사용은 **거치대**다 — 주인님이 총알 거치대를 아무 데나 놓으면 팔이 그 위로 간다.
바꿀 것은 로직이 아니라 **번호 하나**였는데, 코드에 박혀 있어서 못 바꿨다. 위 §기준값은
프로필에 산다가 이미 그 규약이므로 **새 규칙이 아니라 그 규약을 안 지킨 자리를 고친 것이다.**

| 키 | 뜻 |
|---|---|
| `targetTagId` | 어느 태그를 따라가나 |
| `targetSource` | 자리를 어느 창구에서 읽나 — `amr`(터틀봇) · `anchor`(소품) · `color`(글로벌캠 색) · `wrist`(손목캠 깊이) |
| (`color` 산출) `yawDeg` | 2026-09-07 신설 — 색 덩어리의 `minAreaRect` **두 축을 모두 평면에 쏜 뒤, user1 실거리로 더 긴 축**을 고른 거치대 요각(+x 0 · 반시계 + · 180° 대칭이라 `[−90, 90)`). 원근 때문에 화면에서 더 긴 축을 고르면 장·단축이 뒤집힌다. 실거리 종횡비가 1.15 미만이거나 못 내면 `null` — 부르는 쪽은 그때 파지 정본 각을 쓴다(결측=고정각). 파지 벽을 고를 때는 접힌 각을 바로 쓰지 않고 **직전 글로벌캠/패스 각에 가장 가까운 180° 동치 대표**로 편다. `+89.9°` ↔ `−90.1°` 경계에서 긴 벽 신원이 반대로 바뀌는 것을 막는다 |

⛔ **시뮬 탭의 대강값은 출처가 승격되면 즉시 갈아탄다** (2026-09-09 실기). 첫 렌더 직후
`carrier-pose.json` 폴링이 끝나기 전에 「거치대 찾기」를 누르면 `truth-0831` 또는 사람 입력이
먼저 잡힐 수 있다. 그 뒤 신선한 `color(...)`가 들어왔는데도 「이어서 찾기」가 옛 `coarse`와
그 관측 자세를 계속 쓰면 실제 거치대와 수백 mm 떨어진 곳을 보게 된다. 따라서 **fallback
(`truth-0831`·`input`) → fresh color** 승격 시 앞 관측 자세·뷰를 버리고 color 대강값부터 다시
푼다. 반대로 depth 재센터링 값은 글로벌 대강값으로 되돌리지 않는다. `carrier-pose.json`은
상주 검출기가 계속 덮어쓰는 **살아 있는 파일**이므로 화면 폴링은 반드시 `cache: "no-store"`로
읽는다. 브라우저 HTTP 캐시에 맡겨 옛 `t`를 받으면 신선도 검사에서 영원히 fallback으로 내려간다.

### `wrist` — **눈이 팔에 달린 창구** (2026-09-04 신설 · D177)

앞의 셋은 전부 **글로벌캠(폰) 산출물**이다. 그래서 폰이 꺼지면 표적이 통째로 얼어붙는다 —
2026-09-04 에 그렇게 **71분**을 잃었고, 그날 주인님 질문이 *"글로벌카메라없이도 추종가능할지"*
였다. `wrist` 는 그 답이다.

| | 무엇을 보나 | 어떻게 |
|---|---|---|
| 창구 파일 | `Shared/data/config/wrist-pose.json` | `scripts/map/wrist-find.py` 가 쓴다 |
| 표적 | **터틀봇 라이다 윗면 평면** | 손목 뎁스 구름을 user1 로 펴서 무게중심 |
| 사슬 | `camera → tcp → base → user1` | `follow.cam_to_robot` (hand-eye) — **camLab 을 안 지난다** |

⭐ **태그를 안 쓴다.** 글로벌캠 태그 18 은 84mm 가 1126mm 밖에 있어 **45초에 2회(7%)** 만
잡혔다. 손목캠은 **337mm** 에서 평면을 직접 재 16,395점을 얻는다.

⛔ **`amr` 을 대체하지 않는다.** `amr` 은 바퀴로 이어 붙이는 둘째 출처를 갖고, `wrist` 는
**보고 있을 때만** 안다 — 눈이 팔에 달려 있어 화각 밖으로 나가면 못 찾는다. 그래서 이건
**2단(정밀)** 이고, 표적을 화각에 넣는 **1단(대략)** 은 여전히 `amr` 이나 사람이 한다.

⛔ **거치대를 표적으로 쓰지 않는다.** 거치대는 **구멍 판**이라 깊이가 구멍마다 깨진다 —
09-04 실측에서 평면 RMS **13mm**(정상 <2mm)에 *"솟은 것이 없다"* 가 나왔다. 라이다 윗면은
같은 프레임에서 106mm 지름으로 잡힌다. **재는 것과 집는 것을 가른다.**

⚠ **`standoffMm` 을 그대로 못 쓴다.** 프로필의 165 는 **거치대 윗면** 기준이고, 라이다
윗면은 그보다 77mm 높아 카메라가 D435 의 Min-Z **195mm** 안으로 들어간다. `wrist` 를 쓸 때는
**220**(카메라 247mm)으로 올린다 — 08-13 에 잘 됐던 구간 232~273 한복판이다.

⛔ **`targetSource` 는 취향이 아니라 「바퀴가 있나」다.** `amr` 은 태그를 놓쳤을 때
**바퀴(odom)로 이어 붙이는 두 번째 출처**를 갖는다(위 §조건 5 의 출처가 둘). 거치대에는
바퀴가 없다 — `anchor` 는 **태그 하나뿐이고, 못 보면 그냥 멈춘다.** 없는 출처를 있는 척
설정으로 켤 수 없게 값으로 갈랐다.

⚠ **`scene-anchors.json` 은 「못 본 태그의 옛 값을 남기는」 파일이다** (D130 — 소품은 저 혼자
안 움직이니까 그게 옳다). 그 파일을 추종이 읽는 것은 §못 보면(가는 것은 멈춘다)과 **정면으로
충돌하는 것처럼 보인다.** 충돌하지 않는 이유는 하나 — **읽는 쪽이 나이를 본다**
(`FOLLOW_TARGET_MAX_AGE_S`). 파일의 규칙과 읽는 쪽의 규칙이 다를 수 있고, **가는 쪽이 더
엄한 쪽을 쓴다.** ⛔ 이 나이 검사를 지우면 **팔이 옛 자리로 간다** — 파일은 아무 잘못이 없다.

⛔ **사람이 옮기는 물건은 「가려짐」이 기본 상태다.** 손이 태그를 덮으면 앵커는 옛 값에
얼어붙고 나이만 늘어난다 — 그래서 사람이 손을 뗄 때까지 추종은 **사유를 내며 서 있는다.**
그게 옳다: 사람 손이 표적 위에 있는 동안 팔이 그리로 가면 안 된다.

### 손목 스캔 — 표적 셋과 **거울 쌍** (2026-09-07 신설 · D192)

`wrist`(위 · 라이다 윗면 평면 · 추종용)와 달리 **집기 전 정밀 칸**은 `POST /scan`(`API-CONTRACT` §손목 스캔)이 맡는다. 표적은 셋 —
`carrier`(판 위 거치대 · 솟음 55) · `basketFloor`(빈 바구니 바닥 · 파임 = `AMR_BASKET.innerHMm` · 발판 뒤 35) · `carrierInBasket`(내리기 때 바구니 속 거치대 · 윗면이 테두리 위 20). 위 §`wrist` 의
*"거치대를 표적으로 쓰지 않는다"* 는 **평면 피팅** 얘기고, 여기는 **덩어리**(판 위로 솟은 것)라 구멍이 깨져도 발자국이 남는다(`carrier-find.py` · 09-03).

⭐ **거울 쌍이 규약이다.** hand-eye 는 평행이동 셋뿐이고(회전 없음) 08-13 자료를 역산하면 회전 편향이 **3~5°** 라 한 번 보면 @245mm 에서
13~21mm 틀린다 — 손가락↔테두리 여유 4.5mm 를 넘는다. 그래서 정밀 칸은 **수직(tilt 0) · 표적을 화면 중앙에 · 손목 rz 를 180° 돌린 두 자세**
(rz_g+90 / rz_g−90)에서 스캔해 **평균**한다. 툴 프레임에 고정된 오차(평행이동·회전 둘 다)는 툴을 180° 돌리면 부호가 뒤집혀 평균에서 사라진다.
두 값의 차/2 = `halfDiffMm` 가 곧 그 편향의 크기다(진단값 · 다시 재도 안 준다). 통과 = 정확한 거울(180±2°) 그리고 「편향 ≤3mm」 **또는** 「평균 자리로 옮겨 다시 잰 둘째 패스의 평균이 첫 패스와 3mm 안에서 일치」— 일치가 곧 「자세와 무관한 고정 편향」의 증거다. 갈리면 사유를 내고 멈춘다(2026-09-07 실렌더에서 정정 · `Shared/data/sim/aim.js judge`).
근거·크럭스·킬실험: `ref/rnd/AIM2-CONVERGE-LOOP-2026-09-07.md`.

⛔ **거울 쌍이 지우는 것은 「자세와 무관한 고정 편향」만이다.** 거리·화소 위치에 따라 변하는 오차는 안 지워진다 — 그것이 크럭스이고
랩 킬실험(rz/rz+180 × 3자리 · 차 벡터 불변성)이 판정한다. 통과 전에는 이 값으로 **집지 않는다**.

`carrier`의 총알은 정렬 컬러의 분홍 ROI 안에서 황동 연결 성분으로 찾는다. 면적·원형도뿐 아니라
**연결 성분 중앙 채도**를 함께 건다 — 2026-09-10 실기에서 어두운 격자점은 황동 색상 범위에 들었지만
중앙 채도 58이었고, 실제 총알은 현재 129·09-09 저장 프레임 138.5였다. 문턱 80 미만은 버리되,
통과한 성분이 여러 개면 전부 보고한다. 가장 큰 하나를 임의로 고르지 않는다. 황동의 정반사
하이라이트는 밝기 255까지 같은 물체로 이어야 하므로 밝기 상한을 두지 않는다. 2026-09-10 실행
`20260910-134119`에서는 옛 밝기 상한 220이 실제 총알을 조각내 `0/1`로 만들었고, 상한을 제거한
같은 원본은 23×25px·채움 0.40·중앙 채도 93의 한 성분이었다. 색상·채도·면적·형상·ROI·정확히
한 후보라는 나머지 안전 관문은 그대로 둔다. 라이브 반복에서 같은 총알의 위·아래 반사가
17.4px 떨어진 두 성분으로 갈린 경우는 5×5 닫힘으로 4px 이하 틈만 이어 `27×29px` 한 성분으로
합친다. 서로 다른 총알을 좌표 거리로 사후 병합하지 않는다.

`carrier` 한 번의 RGB·뎁스 관측은 동기화 묶음 **9장 중앙값**을 쓴다. 2026-09-10 같은 250mm
정지 자세에서 5장은 깊이 조각이 외곽에 간헐적으로 붙어 거치대 통과가 3/7이었고, 치수·높이
문턱을 그대로 둔 9장은 거치대 1개·총알 1개가 5/5였다. S2의 정지 자세당 최대 3회 재촬영
상한은 그대로이며, 표본을 늘렸다는 이유로 이전 프레임을 재사용하거나 더 하강하지 않는다.

`bulletsUser1Mm`은 검출 보고용으로 끝나지 않는다. S4 고스트의 총알 위치와 MuJoCo 접촉 장면은
반드시 **같은 최신 배열**을 소비한다. `roundsOnBoard` 개수만 보고 거치대 중앙에 총알을 만들어
그리거나, 구운 장면의 과거 고정 총알을 현재 총알 대신 검사하지 않는다. 좌표가 없거나 기대 수와
다르면 고스트·접촉을 통과시키지 않고 S2로 되돌린다. 접촉 장면은 검출 좌표가 바뀔 때 다시 열어야
하며, 손가락뿐 아니라 툴·카메라를 포함한 전체 충돌 형상과 총알을 검사한다.

파지 후보에서 **어느 긴 벽을 물지**(`flip`)와 **손목의 180° 동치 대표**(`turnDeg`)는 독립이다.
평행 그리퍼의 손가락 축은 손목을 180° 돌려도 같으므로, 벽 2×손목 대표 2의 4개를 모두 풀고 총알 간섭이 없으며
IK·안전 게이트를 통과한 후보 중 지금 관절에서 가장 짧은 것을 고른다. 손목 방향을 바꿔 통과시키는 것은 속도·정착 상한을 완화하는 것이 아니며,
선택한 전체 집기·운반·놓기 계획은 S3에서 다시 IK·접촉·작업영역을 검사한다(2026-09-10 실기 `20260910-114547` · D208).
후보뿐 아니라 선택 뒤 `makeLoadSteps`가 내는 **모든 실행 TCP의 `rz`**도 컨트롤러에 묻기 전에
`[−180°, 180°)`로 정규화한다. 후보만 접고 접근·파지·들기 경로를 다시 펴면 후보는 통과하고
실행 계획은 전부 해 없음이 되는 갈림이 생긴다. FAIRINO `GetInverseKinRef`는
같은 자세인 `−181.001°`에는 해 없음을, `+178.999°`에는 안전한 짧은 해를 돌려준 실측이 있으므로
수학적으로 같은 360° 표현을 SDK가 같은 입력으로 처리한다고 가정하지 않는다(`20260910-115804`,
`20260910-141711` · D209).

### 재획득 — **표적을 잃으면 바퀴가 가리키는 곳으로 간다** (2026-09-04 신설 · D180)

주인님 *"표적이 없어지면 터틀봇 위치로 알아서 찾아가야 하는 거 아닌가"*.

`wrist` 는 **보고 있을 때만** 안다 — 눈이 팔에 달려 있어 화각(약 500mm) 밖으로 나가면
영영 못 찾는다. 그러면 사람이 팔을 손으로 돌려 줘야 하고, 그건 자동이 아니다.

⭐ **바퀴는 화각과 무관하다.** 터틀봇은 자기 자리를 늘 말하고 있으므로, 표적을 잃은 순간
**바퀴가 가리키는 곳**을 표적으로 삼아 그 위로 가면 화각에 다시 들어온다.

| | |
|---|---|
| 언제 | `wrist`(또는 다른 창구)가 표적을 못 낼 때 **그때만** |
| 표적 | `odom` → `AMR_HOME` → user1 로 푼 **라이다 윗면** |
| 표시 | `source: "odom"` · `grade: "재획득"` — **글자로 말한다** |

⛔ **몰래 갈아타지 않는다.** `main.py` §표적이 *"눈금이 없으면 바퀴를 안 쓴다 — `AMR_HOME`
으로 몰래 갈아타지 않는다"* 고 못 박은 것을 **어기지 않는다.** 그 금지의 이유는
*"조용히 쓰면 어느 쪽이 답했는지 아무도 모른다"* 였고, 여기는 **출처를 글자로 내보낸다.**

⛔ **재획득은 파지가 아니다.** 이 등급이 열리는 근거가 그것이다 — 표적 **위 standoff**
로 가서 화각에 담기만 한다. `AMR_HOME` 이 실측 대비 **140mm** 어긋나 있어도(2026-09-04)
화각 반지름 안이면 충분하다. **집는 것은 여전히 `wrist` 가 잡은 뒤에만 한다.**

⛔ **바퀴가 낡으면 안 쓴다** — `FOLLOW_ODOM_MAX_AGE_S`. 바퀴는 헛돌아도 태연히 값을 낸다
(2026-08-19 에 제자리인 로봇이 428mm 밖이라고 했다).

⚠ **눈금(`amr-frame.json`)이 서면 이 갈래의 정확도가 mm 급이 된다.** 지금은 `AMR_HOME`
가정값이라 화각 가장자리에 떨어질 수 있다 — 그래서 재획득 뒤에도 **`wrist` 가 잡아야**
비로소 따라간다. 재획득은 **눈을 돌려 주는 것**이지 표적을 대체하는 것이 아니다.

### 조건 5 의 출처가 **둘**이 됐다 (2026-08-31 · D158)

「표적을 지금 보고 있다」의 뜻을 좁혀 적는다. 이제 자리는 두 곳에서 온다 —
**태그**(글로벌캠 · 절대 · 7%)와 **바퀴**(터틀봇 odom · 연속 · 밀린다).
계약은 `API-CONTRACT.md` §터틀봇 자리는 두 출처로 온다가 든다.

| 무엇을 하나 | 무엇을 요구하나 |
|---|---|
| 화면에 **그린다** · **시뮬**로 팔을 움직인다 | 둘 중 하나가 신선하면 된다. **출처를 글자로 말한다** |
| **실기를 움직인다** (단계 3) | `source: "tag"` 이거나, `source: "odom"` 이면 **`correctedAgoS` 가 상한 이내** |

⛔ **바퀴만으로 실기를 움직이지 않는다.** 바퀴는 헛돌아도 태연히 값을 낸다 — 2026-08-19 에
로봇이 제자리인데 odom 은 428mm 밖이라고 했다. 그때 잡아 줄 수 있는 것은 태그뿐이다.

⛔ **못 보면 안 따라간다는 규칙은 그대로다.** 출처가 늘었다고 조건이 느슨해진 것이 아니라,
**같은 조건을 만족시키는 길이 하나 늘었다.**

### 켜는 조건 — 하나라도 빠지면 안 돈다

| # | 조건 | 왜 |
|---|---|---|
| 1 | **사람이 명시적으로 켠다.** 기본은 꺼짐 | 켜는 순간을 사람이 안다. 부팅하며 저절로 돌지 않는다 |
| 2 | 조종권 보유 · `ARMED` | 명령 주인은 한 명이다 (하드 룰 4) |
| 3 | **목표가 게이트를 통과**한다 | 추종이라고 게이트를 우회하지 않는다. `moveJ` 로 번역돼 같은 검사를 탄다 |
| 4 | 속도 **상한 이하** | 하드 룰 3. 새 상한을 만들지 않고 `SAFETY-RULES` §상한을 그대로 쓴다 |
| 5 | **표적을 지금 보고 있다** | 아래 §못 보면 |
| 6 | `stop` 이 언제든 먹는다 | 제3원칙 — 조종권·phase 무관 항상 실행 |
| 7 | **화면이 「지금 자동으로 돌고 있다」를 크게 말한다** | 조용히 도는 것이 제일 위험하다. 사람이 「왜 움직이지?」를 묻는 순간이 오면 안 된다 |
| 8 | **`autoOffAfterS` 가 지나면 스스로 꺼진다** | 조건 1(사람이 켠다)은 **규율이지 안전장치가 아니다.** 끄는 걸 잊는 것이 기본값이므로, 잊어도 꺼지게 만든다 |

⛔ **조건 7·8 이 사람 감시를 대신하지 않는다.** 우리에게 사람을 보는 인증된 층은 없고
(`GOAL-cam-person-watch` §⛔) 이 둘은 **「켜둔 걸 잊는 것」만** 막는다. 자동이 도는 동안
사람이 다가오면 여전히 아무도 못 본다 — **그래서 사람이 곁에 있을 때만 켠다**가 조건 1의
진짜 뜻이고, 8은 그 전제가 조용히 무너지는 것을 시간으로 끊는 장치다.

### 기준값은 **프로필에 산다** — 코드에 박지 않는다

현장이 바뀌면 값이 바뀐다. `config.yaml` 의 `follow:` 블록 하나가 정본이고, 코드는 그것을
읽기만 한다. **기본값을 코드에 두지 않는다** — 두면 설정을 안 고쳐도 돌아버려서 「지금 무슨
값으로 도는가」를 아무도 못 말한다.

| 키 | 뜻 | 근거 |
|---|---|---|
| `standoffMm` | 표면에서 이만큼 떨어져 선다 (TCP 기준) | 카메라 최적 거리 − hand-eye z |
| `faceAxis` | 어느 면을 마주보나 (`z` = 위에서 · `y` = 옆에서) | 눕힌 물체는 `z`, **세우면 `y`** (D122) |
| `deadbandMm` | 목표가 이만큼 안 움직이면 **안 따라간다** | 그 아래는 측정 잡음이다 |
| `releaseMm` | 나갈 때 문턱 (`deadbandMm` 보다 크다) | 같은 문턱이면 경계에서 깜빡인다 (`SHARED-CORE` §판정 규칙) |
| `maxTiltDeg` | 수직에서 이 각도 안 | 넘으면 화면에 평면이 둘 되어 검출이 무너진다 |
| `speedPct` | 이동 속도 | 상한 초과는 게이트가 거부한다 — 여기서 자르지 않는다 |
| `settleMs` | 도착 뒤 이만큼 쉰다 | 다음 측정이 흔들린 프레임을 읽지 않게 |
| `autoOffAfterS` | 켠 뒤 이만큼 지나면 **스스로 꺼진다** | 조건 8 — 끄는 걸 잊어도 꺼진다 |

⭐ **`faceAxis` 가 이 표의 핵심이다.** 지금은 눕힌 물체를 **위에서** 보지만, 세워 꽂으면
**옆에서** 봐야 한다 (D122 — *"위에서 못 보므로 접근은 옆에서"*). 「위」를 코드에 박으면
그날 다시 짜야 한다. **기준을 「표면에서 얼마 · 그 표면을 정면으로」로 일반화**해 두면
바뀌는 것은 이 값 하나다.

### hand-eye 유효성 — **프로필에 있나 하나로 판정한다** (2026-08-27 · D145)

`handEye` 도 위 `follow:` 와 같은 규약이다 — 프로필이 정본이고 코드에 기본값을 두지 않는다.
*"캘리브가 안 된 셀에서 남의 값으로 조용히 도는 것이 제일 나쁘다"* (`follow.py` §`cam_to_robot`).

| 키 | 뜻 |
|---|---|
| `tMm` | TCP→카메라 평행이동 셋. **없으면 카메라 좌표를 로봇 좌표로 못 옮긴다 → 차단** |
| `spreadMm` | 여러 자세가 같은 점을 가리킨 흩어짐. 판정이 아니라 **정확도 고지**다 |
| `measuredAt` | 언제 쟀나. 이것도 판정이 아니라 고지다 |
| `biasCorrectedAt` | (2026-09-07 신설) 거울 쌍 실측으로 `tMm` xy 를 **사람이** 고친 날. 고지 |
| `residualMm` | (2026-09-07 신설) 고친 뒤 **한 눈**이 진값(거울 쌍 평균)에서 벗어난 잔차 평균. 고지 |
| `singleView` | (2026-09-07 신설) `true` 면 마법사 ①이 **스캔 A 한 번으로 판정**한다 — 자세 B·두 번째 보기가 사라진다. 없거나 `false` 면 두 눈(거울 쌍) |

**한 눈 판정의 근거 (2026-09-07 랩 · `evidence/2026-09-07/handeye-bias-from-mirror-pairs.md`)** — 거울 쌍 4패스·14눈에서 「눈 − 평균」을 툴 좌표계로 돌리면
**(+15.2 ± 0.9, −13.5 ± 1.9)mm 로 전부 같았다.** 즉 오차는 자세가 아니라 `tMm` xy 에 붙은 고정값이고, 그만큼 `tMm` 을 고치면 한 눈 잔차가 평균 1.9 · 최대 3.4mm 다.
이 값은 자동으로 덮지 않았다(아래 ⛔ 그대로) — 데이터를 보고 사람이 프로필을 고쳤다. rz 180 쪽과 0 쪽이 y 로 약 4mm 체계적으로 갈리는 잔차(카메라 롤)가 남아 있어
파지 여유(4.5)에 가깝다 — `singleView` 를 켠 로봇도 「자세히」에서 B 를 켜 검산할 수 있다.

**판정은 `tMm` 존재 하나뿐이고, 나머지 둘은 사람에게 보이기 위한 값이다.** 문턱을 여기에
두지 않는다 — 「흩어짐 몇 mm 부터 거부」를 정하려면 작업이 요구하는 여유를 알아야 하는데,
그건 물체마다 다르다(D122 는 세워 꽂기에서 ±10mm 라고만 말한다).

**⛔ 자동 보정하지 않는다.** `tMm[2]` 는 핑거 길이에 딸린 값이라(`DEPTH-CAM.md` §80 은
핑거에 딸린 값이다) 산술로 밀 수 **있지만**, 그때 브래킷을 건드렸는지는 아무도 모른다.
자동으로 SSOT 를 덮는 경로는 이미 갭이 열려 있다 — **사람이 다시 재고 프로필을 고친다.**

**상태에 싣는다.** `GET /state` 의 `handEye` 로 나간다 — `workspace` 와 같은 이유다
(*"없으면 손끝 판정이 꺼진 것이다 — 조용히 사라지지 않게 노출한다"* · `session.py`).
정적 값이지만 **없다는 사실이 화면에 보여야** 하므로 같은 자리에 둔다.

⚠ **`calibId` 와 헷갈리지 않는다** — 그건 관문의 장치 동일성이지 이 판정이 아니다
(`LAYOUT-METRICS-CONTRACT.md` §`calibId` 는 프레임 출처 참조 하나다).

### ⛔ 못 보면 — **멈춘다** (마지막 자리로 가지 않는다)

§움직이는 장애물(D130)은 표적을 놓쳐도 **마지막 자리를 유지**한다. **추종은 반대다.**

- 게이트 상자는 **막는 쪽**이라 낡은 값이라도 남는 게 안전하다
- 추종은 **가는 쪽**이라 낡은 값으로 가면 **모르는 자리로 팔을 보낸다**

같은 결측인데 처방이 반대인 것이 요점이다. **가는 것은 멈추고, 막는 것은 남는다.**

### 추종은 **파지하지 않는다**

안전 거리를 유지할 뿐이고, 내려가 무는 것은 이 절의 범위 밖이다. 파지는 여전히
§제안 → 사람 승인을 탄다. **추종이 파지의 문을 열어 주지 않는다.**

### TCP 는 **핑거 끝**이다 — `targetPose` 는 물체가 아니라 손끝 자리다 (2026-08-10 · D108)

**결정: TCP 기준점은 핑거 끝(플랜지 +135mm)이고, 바꾸지 않는다.**

- 툴 `[0,0,135,0,0,0]` 의 135 는 **플랜지→핑거 끝 실물 실측과 일치**한다
  (몸통 90 + 판 20 + 핑거 25 · 2026-08-05 줄자). 2026-08-10 **실기 되읽기로 재확인** —
  `appliedSettings.readback.toolCoord` = `[0,0,135,0,0,0]` · `mismatch: []`
- **파지 중심(≈122.5)으로 옮기지 않는다.** 그 값은 **잴 수 있는 대상이 아니다** — 얼마나
  깊이 무느냐에 따라 달라진다. 툴에 박으면 작업마다 다른 값이 **암묵적 계통 오차**로 산다

⛔ **그래서 이 한 줄이 계약이다:**

> **`targetPose.tcpMmDeg` 는 「물체가 어디 있나」가 아니라 「손끝을 어디 두라」다.**
> 물체 위치 → 손끝 목표 변환(= 삽입 깊이)은 **제안을 만드는 쪽이 명시적으로** 한다.

비전이 물체 중심을 그대로 실으면 손끝이 물체 한복판으로 들어간다 — 파지 실패가 아니라
**충돌**이다. 오차를 툴에 숨기지 않고 **작업이 말하게** 하는 것이 이 결정의 전부다.

### ⛔ 대신 남는 게이트 — 잴 때와 실행할 때 툴이 같아야 한다

기준점이 정해져도 **그 기준이 실행 순간에도 유효한지**는 따로 봐야 한다. 제안은 이미
`toolId`·`userId`(잴 때의 좌표계)를 싣는다(위 §제안). **번역·실행 직전에 실기의 `coord` 와
`coordDefs.tool` 을 대조**해 다르면 `rejected`(**`toolFrameMismatch`**) 한다.

- `validUntil` 을 두 번 검사하는 것과 같은 이유다 — 대기 중에 사람이 좌표계를 바꿀 수 있다
- ⚠ **실기는 `tool 1 · user 1` 로 돈다.** `config.yaml` 의 `toolCoordId: 0` 은 선언일 뿐
  적용된 적이 없고, **적용하면 TCP 가 135mm 튀며 작업영역 게이트가 거짓이 된다**
  (`GAP-MATRIX` · `config.yaml:56` ⛔). 이 대조가 그 사고를 실행 직전에 잡는다
- 이 검사는 **비전 전용 상한이 아니다** — 좌표계가 바뀌었는지 보는 것이라 §못 박는 것 다섯의
  「비전용 상한을 따로 두지 않는다」에 안 걸린다

⚠ **사유 이름이 두 번 갈렸다** — `toolCalibrationUnverified`(캘리브 미검증 · **거짓이 됨**)
→ `tcpDatumUndecided`(기준점 미정 · **오늘 정해짐**) → **`toolFrameMismatch`**. 소비처가
0건이라 매번 공짜였다. **라벨이 거짓이 된 순간 가는 것을 미루지 않는다** (D106).
