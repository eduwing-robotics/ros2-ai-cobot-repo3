# 프로그램 슬롯 계약 — 지점을 순서로 엮어 승인한 것만 실행한다

FR5 사다리 3. 골은 [`GOAL-program-slots.md`](../../goals/GOAL-program-slots.md).
**`API-CONTRACT.md` 가 아니라 여기 산다** — 그 문서가 이미 450줄 상한에 닿았고, 슬롯은
수명주기(draft→approved)와 소비자(Program 화면)가 상태·명령과 다르다 (카메라·제안을 뺀 것과 같은 이유).

## 이 계약이 지키는 것

**실기에 닿는 cmd 허용목록에 새 이름을 더하지 않는다.** 슬롯 실행은 `moveJ` 를 통해서만
하드웨어에 닿고, 그 경로는 `POST /points/{name}/goto` 가 이미 쓰는 것과 **같은 함수**다 —
경로 검사(D75)·작업영역·26조건을 매 단계 처음부터 다시 탄다. 슬롯이라고 게이트를 건너뛰지 않는다.

## 지금 여는 것과 안 여는 것

`GOAL-program-slots.md` 의 Outcome 7개 중 **1·4·6** + **7의 절반(`grip`)** 을 연다.

| 연다 | |
|---|---|
| 1 | 지점을 골라 **단계 목록**으로 엮는다 |
| 4 | `approved` 인 슬롯만 실행하고, **실행 직전에 승인 당시 정체와 지금을 재대조**한다 |
| 6 | **한 단계씩 실행이 기본** — 한 번의 요청이 한 단계만 움직인다 |
| 7 (절반) | **`grip` 칸** — 아래 §grip 칸. `move` 로 한 바퀴를 돈 조건이 2026-08-08 에 채워졌다 |

| 천장 — 이번에 안 연다 | 왜 |
|---|---|
| 불변 리비전 (Outcome 2) | 수정하면 `draft` 로 되돌리는 것으로 대신한다. 리비전이 필요해지면 그때 스키마를 늘린다 |
| 중단 후 재개·커서 (Outcome 5) | 서버가 커서를 안 든다. 몇 번째를 실행할지는 **요청이 지정한다** — 재개 로직이 아예 없으므로 "자동 재개"도 없다 |
| `wait` 단계 (Outcome 7 의 나머지) | 대기는 시간을 계약에 박는 일이라 실측이 먼저다. `grip` 이 대기를 대신하는 자리가 많다 (닫힘 완료를 서버가 기다린다) |
| **묶음 「집기」 스킬** | Doosan `Pick`/`Place` 처럼 접근·닫기·상승을 한 칸에 넣는 것. 칸이 여럿을 숨기면 **승인이 무엇을 승인했는지가 흐려진다** — 지금 승인은 「칸 하나 = 명령 하나」에 걸려 있다. 필요해지면 그때 **승인 단위**부터 다시 정한다 |
| 이동 중 미리 발사 | KUKA `Trigger When Distance`·ABB `TriggIO` 처럼 끝점 n mm 전에 그리퍼를 쏘는 것. 사이클타임 최적화지 기능이 아니고, **경로 검사(D75)가 보는 구간 안에서 손이 움직인다** — 게이트를 다시 설계해야 한다 |
| 분기·조건 | 선형 목록만. 조건 분기는 다음 골이다 |

**연속 실행·반복은 2026-08-08 에 열렸다** — 조건이 채워졌기 때문이다. 아래 §연속 실행.

  // 재교시된(아무도 검토 안 한) 자세가 옛 승인으로 나간다 (감사 #2). 실행 직전에 대조한다

## `grip` 칸 — 그리퍼는 이동의 **속성**이 아니라 독립 **칸**이다 (2026-08-10 잠금)

```jsonc
{ "type": "grip", "pct": 0 }     // 0~100 정수. 다른 필드는 없다
```

**업계가 만장일치인 자리다** — 확인한 펜던트 전부 티칭 포인트에 그리퍼를 담지 않는다.
UR+Robotiq 은 Waypoint 와 나란한 **`Gripper` 노드**(문서가 *"Waypoints do not store gripper
state"* 를 명시), FANUC 은 `RO[n]=ON` **별도 줄**, ABB 는 `robtarget` 밖의 `Set`·`TriggIO`,
KUKA 는 출력 + `TRIGGER`. 우리도 같은 자리에 둔다. **우리가 그 판단에 도달한 경로는 달랐다** —
지점에 딸려 붙이면 ①벌린 채로 잰 지점에 물건을 쥐고 가면 **떨어뜨리고** ②집기는
「접근(열림) → 하강 → **닫기**」라 이동과 동시에 닫으면 **내려가는 길에 부품을 친다**.

| 잠그는 것 | 값 | 왜 |
|---|---|---|
| **필드** | **`pct` 하나만** | `speed`·`force` 는 서버 상수로 남는다. `force 30%` 가 충분한지 **아직 안 재봤다**(`GAP-MATRIX`) — 근거 없는 값을 계약에 박는 것이 `/스택가드` 가 막는 일이다. UR 은 `Position`·`Speed`·`Force` 셋을 열지만 그쪽은 실측이 있다. 재고 나면 **그때 필드를 연다** |
| **대기** | 서버가 **완료까지 기다린다** (고정) | UR 은 `Complete motion` 토글을 준다. 우리는 **한 요청 = 한 단계**(D78)라 비동기 칸이 애초에 성립하지 않는다 — 토글을 만들면 "안 기다린 칸" 다음 칸이 무엇을 보장하는지가 새 질문이 된다 |
| **번역** | `grip` 칸 → `cmd: "gripper"` | `move`→`moveJ` 와 **같은 규약**이다. **실기 cmd 허용목록에 새 이름을 더하지 않는다** (§이 계약이 지키는 것) |
| **게이트** | 그리퍼 전용 (`API-CONTRACT.md` §그리퍼) | 5°·URDF 한계·모션큐를 걸지 않는다. 조종권 · ARMED · 상태 신선도 · `gripperFault` 없음 · 힘 상한 · `maxtime` 은 `vel` 에서 유도. 관절 게이트를 복붙하면 통과 자체가 불가능하다 (감사 P1) |
| **지문 대조** | **대상 아님** | `grip` 칸은 `pointName` 이 없다 → 재교시로 승인이 풀리지 않고, 지점 삭제 참조에도 안 걸린다. `approvedWith.points` 는 `move` 칸만 모은다 |
| **승인** | `move` 와 같다 | `steps` 가 바뀌면 `draft`. `grip` 칸의 `pct` 를 고치는 것도 `steps` 변경이다 — **어느 폭으로 쥐는지가 승인 대상**이기 때문이다 |
| **거부 사유** | `pct` 가 0~100 정수가 아니다 · 그리퍼가 활성화되지 않았다(`active` 비트 0) · `gripperFault` · 그리퍼 미장착(`toolId` 가 프로필의 그리퍼 좌표계가 아니다) | 사유는 사람 말로 낸다. 추측으로 고치지 않는다 |
| **`pct` 의미** | **`0` 닫힘 · `100` 열림 (= 벌어짐 정도)** | ⚠ **2026-08-10 정정 — 처음 이 표에 「0 열림·100 닫힘」으로 거꾸로 적었다.** 정본은 셋이 한 방향을 가리킨다: `main.py` 의 `open:true → pct 100` · 조작대의 `완전 열기 → send(100)` · `gripMm = pct × 행정 / 100`(클수록 벌어짐). **거꾸로 적으면 「닫기」 칸이 손을 열어 물건을 떨어뜨린다** — 이 계약이 막으려던 그 사고다 |

### 삽입은 단계 옆에서, 저장은 독립 칸으로

**사람의 제스처와 저장 모양을 갈라 둔다.** 단계 목록의 각 줄에 `+ 손` 버튼을 두고, 누르면
**그 줄 뒤에** `grip` 칸이 꽂힌다 — 눈에는 "이 지점 다음에 손을 닫는다"로 보이고, 데이터는
낙하·순서 사고가 안 나는 모양으로 남는다. `pct` 기본값은 **그 줄이 가리키는 지점에서 캡처된
`gripperPct`** 를 넣되 화면이 **「이 지점에서 잰 값 62%」라고 출처를 적는다** — 자동으로
넣고 말 안 하면 그게 "지점이 그리퍼를 재생한다"는 오해를 다시 만든다 (그 오해를 끊은 게
`grip-not-replayed` 안내다).

⚠ **처음엔 「Teach 의 지점 카드에 버튼을 둔다」로 적었는데 구조가 아니었다** (2026-08-10
구현 중 정정). Teach 패널은 **어느 슬롯이 초안인지 모른다** — 단계 편집(`step-add`·
`step-up`·`step-remove`)은 전부 Program 이 들고 있다. 그대로 하려면 두 패널이 초안을
공유하는 **새 교차 상태**가 필요하고, 그건 이 계약이 D78 이후 계속 피해 온 모양이다.
그리고 사람이 「이 지점 다음에 손을 닫자」고 생각하는 순간은 **단계 목록을 보고 있을 때**라
버튼도 거기 있는 게 맞다. 지점 이름은 그 목록에 이미 적혀 있다.

- **`「이동」은 관절만 보낸다`는 문구는 남는다.** `grip` 칸이 생겨도 `goto` 는 여전히 손가락을
  안 움직인다 — 이 계약은 그 판단을 뒤집지 않고 **이어받는다**
- 칸 이름은 **값에서 만든다 — 「손 N% 로」 한 형태.** 이동 칸과 **문법을 맞춘다**:
  `trayPick 으로` / `손 42% 로` — 둘 다 「…으로 보낸다」라 목록에 동사가 하나다.
  사람이 이름을 지으면 목록이 스스로 읽히지 않는다(Robotiq 의 자동 명명과 같은 이유).
  ⚠ **열기/닫기 같은 동사를 라벨에 넣지 않는다** — 숫자가 바로 옆에 있어 중복이고, 무엇보다
  **방향을 한 번 틀리면 이름과 동작이 반대가 된다**(2026-08-10 에 실제로 그랬다:
  「손 닫기」가 손을 열었다). **방향의 정본은 라벨이 아니라 ①입력칸 툴팁
  (`0 = 완전히 닫힘 · 100 = 완전히 열림`) ②§집기 순서 안내** 둘이다
- **잡았는지 확인하는 일은 다른 칸이다** (Robotiq 의 `Grip Check` 가 별도 노드인 것과 같다) —
  지금은 안 연다. 파지 확인 실측이 닫히기 전에는 무엇을 근거로 판정할지가 없다

### 착수 선행 — 계약은 잠가도 되고, 구현은 아직 아니다

**계약 모양은 파지 실측에 흔들리지 않는다** — 실측이 바꾸는 것은 서버 상수(`force`·`vel`)뿐이고
`{type,pct}` 는 그대로다. 그래서 이 절은 지금 잠근다. 다만 **구현 착수는 막혀 있다**:

- ⛔ `force 30%` 가 물건을 드는 데 충분한지 모른다 (`GAP-MATRIX`)
- ⛔ **물건을 잡으면 행정이 안 끝나는데** 컨트롤러가 완료로 보는지 `maxtime` 을 세는지 모른다
  — 이게 「서버가 완료까지 기다린다」의 근거를 정한다. 세는 쪽이면 **정상 파지가 timeout 으로
  래치**될 수 있다 (2026-08-04 에 전원 재투입까지 갔던 그 고장)

둘 다 **잡을 물건 하나 + 30분** 킬실험 한 번으로 닫힌다. **서버·화면은 mock 왕복까지 만들어도
되지만, 실기 집기 한 바퀴는 그 실험 뒤다.**

## 엔드포인트

```
GET    /slots                                        → [{ …위 스키마 }]  (누구나)
POST   /slots            { who, token, name, steps } → 만들거나 덮어쓴다. 항상 draft 로 돌아간다
DELETE /slots/{name}     { who, token }
POST   /slots/{name}/approve { who, token, confirm: "현장확인" }
POST   /slots/{name}/step    { who, token, index, speedPct? } → index 단계 하나만 실행 (속도 1~10, 없으면 10)
```

**읽기는 누구나, 쓰기는 조종권자만** (D44). 응답은 성공 `{ "ok": true, …, "reasons": [] }`,
거부 `{ "ok": false, "reasons": [...] }` — 기존 라우트와 같은 모양이다.

### `POST /slots` — 고치면 승인이 풀린다

`steps` 를 바꾸면 **무조건 `draft` 로 되돌아간다.** 승인은 그 순간의 단계 목록에 대한 것이라,
목록이 바뀌면 그 승인은 다른 프로그램의 승인이다. 리비전이 없는 지금은 이게 그 자리를 대신한다.

- `name` 은 `safe_name`(`^[A-Za-z0-9가-힣_-]{1,64}$`)을 지난다 — 파일 이름이 되기 때문이다 (감사 P0-2)
- `steps` 는 1~50개. `pointName` 이 **없는 지점을 가리키면 저장 자체를 거부**한다 —
  실행 시점에야 드러나면 로봇 앞에서 알게 된다
- 단계 0개는 거부한다. 빈 프로그램을 승인할 수 있으면 승인이 무의미해진다

### `POST /slots/{name}/approve` — `arm` 과 같은 관문

조종권 + `confirm: "현장확인"` 을 요구한다. **위험한 동작은 전부 같은 모양**이라는 계획 §확인 절차
그대로다 — 화면은 `[ ] <무슨 일이 일어나는지 한 줄>` 체크박스 + 실행 버튼을 쓴다.

승인 시점의 `robotId`·`toolId`·`userId`·**`toolCoordMm`**·`firmware` 를 `approvedWith` 에 박는다.
**ARMED 를 요구하지 않는다** — 승인은 로봇을 움직이지 않는다.

`toolCoordMm` 는 **캐시가 아니라 그 자리에서 다시 읽은 값**이다. `/state.coordDefs` 는 번호가
같으면 캐시를 주므로(`session._coord_defs`), 번호가 그대로인 채 값만 바뀌는 바로 그 사건에서
옛 값을 계속 내놓는다 — 판정에 쓰는 경로는 캐시를 안 탄다. 못 읽으면 승인하지 않는다
(제1원칙: 결측=차단). mock 은 `[0,0,0,0,0,0]` 을 내므로 값이 있는 것으로 친다.

### 속도는 단계마다 고른다 — 승인에는 안 들어간다

`speedPct` 는 **요청에 실리지 슬롯에 저장되지 않는다.** 승인은 「어디를 어떤 순서로 가는가」에
대한 것이고, 속도는 그때그때 사람이 정한다 — 슬롯에 굳히면 그 값을 바꾸는 것도 승인 대상이
되어야 하고, 그러면 천천히 한 번 돌려보려고 승인을 다시 받아야 한다.

상한(10%)은 **서버가 지킨다** — `safety.check_motion` 이 `0 < speedPct ≤ 10` 을 다시 보고
넘으면 거부한다 (하드 룰 3). 화면이 보내는 값은 편의지 안전장치가 아니다.

⚠ 속도를 사람이 고르게 된 이상, 기록(`GOAL-run-history` 의 `stamp`)은 **상한이 아니라 그때
실제로 쓴 값**을 남겨야 한다. 안 그러면 3% 로 잰 것과 10% 로 잰 것이 같은 조건으로 비교된다.

### 재교시 — 지점을 다시 가르치면 승인이 풀린다

지점은 **이름으로만 참조**한다(위 §모양). 그래서 같은 이름으로 다시 캡처하면 승인된
프로그램의 **동작이 승인 없이 바뀐다.** 방어선은 둘이고, 둘 다 있어야 한다:

| 언제 | 무엇 | 왜 둘 다인가 |
|---|---|---|
| **캡처 순간** | `POST /points` 가 그 지점을 쓰는 승인 슬롯을 `draft` 로 되돌리고 이름들을 응답 `unapproved` 에 싣는다 | 이 계약이 *"없는 지점을 가리키면 저장 자체를 거부한다"* 로 택한 것과 같은 이유 — **알 수 있는 가장 이른 곳**에서 알린다 |
| **실행 직전** | `approvedWith.points` 지문 대조 (감사 #2) | 최후 방어선. 파일을 손으로 고쳤거나 캡처 경로를 안 지난 변경도 여기서 걸린다 |

앞의 것은 **알림이지 안전장치가 아니다.** 뒤의 것을 지우면 안 된다.

### `POST /slots/{name}/step` — 한 번에 한 단계

0. **`ARMED` 가 아니면 거부한다.** `goto` 라우트가 게이트 앞에서 명시적으로 보는 것과 같다 —
   "안쪽 게이트가 어차피 막는다" 에 기대지 않는다. 거부 사유가 `phase` 로 나와야 화면이
   "ARM 하세요" 를 말할 수 있다
1. `status == "approved"` 가 아니면 거부 (Outcome 4)
2. `approvedWith` 와 **지금 세션**을 대조 — `robotId`·`toolId`·`userId`·`toolCoordMm` 가 다르면
   fail-closed. 그리퍼 장착 전(tool0)에 승인한 것을 장착 후에 실행하면 TCP 오프셋만큼 어긋나
   **파지 실패가 아니라 충돌**이 된다 (§이동 지점의 감사 P0 와 같은 뿌리).

   **번호 셋만으로는 절반이다.** 지점은 관절값으로 재생되므로(`MoveJ`) 팔 자세는 승인 때와
   똑같은데, 툴 오프셋이 바뀌면 **손끝만 그 차이만큼 더 나간다.** 핑거를 25mm 에서 40mm 로
   갈면 승인된 하강이 15mm 더 깊어지고, 번호 대조·지점 지문·작업영역(`check_workspace`)
   **어느 것도 안 걸린다** — 작업영역은 손끝 좌표로 판정하는데 그 좌표를 만드는 툴 값 자체가
   바뀌었기 때문이다. 그래서 값을 지문에 넣는다
3. `index` 가 범위 밖이면 거부
4. 칸 종류로 갈린다 — **게이트가 다르기 때문이다** (§grip 칸):
   - `move` → 그 단계의 `pointName` 을 **`goto` 와 같은 경로로** 보낸다. 개체 귀속·좌표계·
     경로 검사·26조건을 전부 다시 탄다. ARMED 는 그 게이트가 요구한다
   - `grip` → `cmd: "gripper"` 와 **같은 경로로** 보낸다. 그리퍼 전용 게이트를 타고,
     관절 게이트(5°·URDF·모션큐)는 타지 않는다. 완료까지 기다린 뒤 응답한다

**한 요청이 한 단계다.** 서버는 "다음 단계"를 모른다 — 화면이 몇 번째를 눌렀는지 보낸다.
그래서 중단해도 재개할 상태가 없고, 처음부터 다시 도는 사고도 구조적으로 없다.

**그래서 임의 칸 실행이 공짜로 열린다** (2026-08-10 · 화면에 「이 칸만」 버튼). `index` 를
서버가 검사하는 것은 **범위**뿐이고 순서가 아니다 — 3번 칸만 눌러 시험할 수 있다.
⚠ **순서를 건너뛰는 책임은 사람에게 있다** — 접근 없이 하강하면 부품을 친다. 다만 게이트
(경로 검사 D75·작업영역·26조건)는 **매 칸 처음부터 다시 타므로** 충돌 경로면 거부된다.
화면은 그 문장을 실행 버튼 옆에 적는다. **서버는 한 줄도 안 바뀐다.**

## 연속 실행과 반복 (2026-08-08 · D94)

**원래 요구사항이다** — `USER-REQUIREMENTS.md` UR_07「여러 자세를 순서대로 이어 **반복
실행**」· SR_07「1회·반복 실행한다」. 미룬 것이지 접은 게 아니었고, 골이 건 조건
「한 바퀴를 단계별로 통과시킨 **뒤에** 연다」가 실기에서 채워졌다.

### 서버는 여전히 커서를 안 든다 — **화면이 돈다**

새 엔드포인트를 만들지 않는다. 연속 실행은 화면이 `POST /slots/{name}/step` 을
`index` 를 올려 가며 **순서대로 부르는 것**이고, 서버 쪽은 한 줄도 안 바뀐다.

| 왜 이렇게 하나 | |
|---|---|
| **게이트가 그대로 산다** | 매 단계가 ARMED·승인·정체 지문·경로 검사·26조건을 처음부터 다시 탄다. 서버가 도는 루프를 만들면 그 안에서 게이트를 몇 번 타는지가 새 질문이 된다 |
| **탭을 닫으면 멈춘다** | 화면이 도니 브라우저가 죽으면 다음 단계가 안 나간다 — 사람이 자리를 뜨면 멈추는 쪽이 기본값이어야 한다 (하드 룰 3) |
| **재개 상태가 안 생긴다** | D78 그대로. 서버에 커서가 없으니 "자동 재개" 도 여전히 없다 |
| **다음 단계를 언제 보낼지 이미 안다** | `commands.settle_seconds()`(실측 · 2026-08-08)가 이동이 끝난 뒤에 응답한다. 화면은 응답을 기다렸다 다음을 부르면 된다 — 폴링하지 않는다 |

### 규약

- **거부 하나면 즉시 전부 멈춘다** (fail-closed). 남은 단계·남은 회차를 진행하지 않고
  사유를 그대로 보여준다. 「한 단계 건너뛰고 계속」 은 없다
- **반복은 1~20회.** 무한은 열지 않는다 — 사람이 없는 사이 도는 로봇을 하드 룰 3 이 금지한다.
  천장: 진짜 양산 반복이 필요해지면 그때 **회차 상한이 아니라 감시 방식**부터 정한다
- **「그만」 은 루프만 멈춘다.** 이미 나간 단계는 끝까지 간다 — 로봇을 세우는 것은 `STOP` 이다.
  화면이 그 차이를 문장으로 말해야 한다
- **한 단계씩 실행은 없애지 않는다.** 기본은 여전히 single-step 이고, 연속 실행은 그 옆에 선다
- 속도는 §속도 그대로 — 회차마다 다시 고르지 않고 시작할 때 고른 값이 전 회차에 쓰인다
